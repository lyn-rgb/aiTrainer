# aiTrainer 架构

> 本文只描述**当前代码里真实存在的东西**。每条依赖规则都由
> `pyproject.toml` 里的 import-linter 契约机器校验，所以它不会漂移。
>
> 未实现的设计构想见 `路线图.md`；缺陷与验证记录见 `代码审计报告.md`。

---

## 1. 分层

依赖只能自上而下。同一层内允许互相导入。契约在 `pyproject.toml` 的
`[tool.importlinter]`，`lint-imports` 是 CI 的一步。

```
L5  接口      api.py · cli.py
L4  编排      trainer/ · parallelizer.py · diagnostics.py · loading.py
L3  策略      offload/ · plugins/ · planner.py
L2  平台      parallel/ · mesh.py · checkpoint/ · overlap/ · memory/
              runtime.py · distributed_model.py
L1  声明      config/ · capability.py · precision.py · data.py · topology.py
              presets.py · metrics.py · profiler.py · kernels/ · adapters.py
L0  地基      core/
```

### L0 `core/` —— 叶子层

不 import `aitrainer` 里任何其他模块。这是整个分层唯一必须靠约定保证的边界，
所以它由三条契约中的一条单独守着。

| 模块 | 内容 |
|---|---|
| `core/torch.py` | **唯一**的可选 torch 策略：`require_torch` / `dist` / `is_distributed` / `world_size` / `rank` |
| `core/dtypes.py` | `dtype_name`（统一 strip + lower）、`resolve_dtype_name`、`dtype_size` |
| `core/tensors.py` | `walk`（谓词由调用方给）、`move_to`、`map_tensors`、`tensor_bytes` |
| `core/batching.py` | 批处理约定：`TARGET_KEYS`、`model_inputs`、`target_of`、`split_microbatches`、`normalize_loss`、**`compute_loss`（全仓唯一一份）** |
| `core/lifecycle.py` | `AsyncOp` / `State` / `ExecutionScheduler` |

**`core/batching.py` 是解开循环依赖的关键**：批处理约定既不是「并行」也不是「数据契约」，
把它们放在两者下方之后，`data → parallel` 与 `parallel → data` 这两条边同时消失。

### L1 声明层

配置模式、契约、能力登记、硬件描述。torch 可选且惰性，不拥有任何运行时资源。

- `config/` 拆成 `errors.py` / `codec.py` / `schema.py`：
  - `schema.py` 放 dataclass 与**各自的**不变量校验
  - `codec.py` **从类型注解反射出嵌套结构**（`nested_config_types`），
    所以新增一个嵌套配置不需要改解析器
- `capability.py` 拥有**跨配置**的规则（`validate_combinations`），
  以及公开入口 `validate_capabilities`（先跑 schema 校验，再跑组合规则）

### L2 平台层

进程组、集合通信、流水线协议、检查点 IO、异步基座、缓冲区池。

**`parallel/fsdp.py` 是 FSDP2（`torch.distributed.fsdp.fully_shard`），不是 FSDP1 的
包装类**。没有 `FSDPWrapper`：`fully_shard` 就地改造模块并返回同一个对象，所以
`wrap_fsdp` 返回的就是传进去的模块（实例的类会被换成动态生成的 `FSDP<类名>`，
`type(x).__name__` 因此变了而 `x is module` 仍为真）。以下四条是实测得到的
语义，写错都不报错，只会改变数值或性能：

| 事项 | FSDP2 的答案 | 写错的后果 |
|---|---|---|
| 累积窗口内抑制归约 | `no_gradient_sync` → `set_requires_gradient_sync(False)` | 每个 microbatch 一次完整归约。**窗口内 `.grad` 一直是 `None`**（缓存在内部），下一个**同步**的 backward 才把所有累积一次性归约（实测 `4 * unit`，不是 `1 * unit`）——所以窗口中途做 optimizer step 是静默无效的 |
| 梯度裁剪 | `parallel.fsdp.clip_grad_norm_`（自己归约） | FSDP2 没有 `module.clip_grad_norm_`，`torch.distributed.fsdp.clip_grad_norm_` 在 2.9 **不存在**。而 `nn.utils.clip_grad_norm_` **不是**等价替代：DTensor 确实注册了 `linalg.vector_norm`（返回 `_NormPartial`），但 `nn.utils` 用 `torch.stack` 把各参数结果堆起来，这个 stack 不认 DTensor，**静默退化成各分片自己的范数** —— 实测 dp=2 时两个 rank 分别报出 0.551 / 0.395，而全局范数是 0.678：每个 rank 会按**不同**系数裁剪。`clip_grad_norm_` 因此自己做归约，并在「输入是 DTensor 但范数不是」时**报错**而不是照常裁剪 |
| 取全局 state dict | `get_model_state_dict(..., StateDictOptions(full_state_dict=True))` | 没有 `full_state_dict_context`；默认返回的是 DTensor |
| 构造 device mesh | `wrap_fsdp` 自己建 | `fully_shard` 不带 mesh 会走 env:// rendezvous，`world_size==1` 时报 `environment variable RANK expected`——既没提 FSDP 也没提进程组 |
| DP mesh 必须是**同一父 mesh 的子 mesh** | `parallel.fsdp.dp_axis_mesh` 取 `mesh.submesh("dp")` | DP group 与 dp 子 mesh 覆盖同一批 rank，看着可互换，**并不是**：`DeviceMesh.from_group` 造出的是没有父 mesh 的独立 mesh。模块里一旦有 TP 的 DTensor 参数，FSDP2 就要求两者共享父 mesh，否则构造期报 `FSDP requires the DP and model parallel TP/EP mesh to have the same parent mesh`。实测：`tp_size=2 + fsdp.enabled` 挂，`dp_size=2` 单独跑没事 |

### TP / SP 也是 DTensor（`parallel/tp.py`）

**参数是 `DTensor` 而不是「装着分片的普通 `Parameter`」**，这是分片 checkpoint 能成立的前提：

| 事项 | 现在的答案 | 为什么 |
|---|---|---|
| 切分投影 | `torch.distributed.tensor.parallel.parallelize_module` + `ColwiseParallel`/`RowwiseParallel` | 旧的自研层把权重换成**分片形状的普通 Parameter**，没有任何地方记录它是某个更大逻辑张量的一片——于是 `get_model_state_dict` 返回局部张量，DCP 把同名 key 当成同一个逻辑张量，最后写入者胜出。`parallelize_module` 只替换**参数**，不更换子模块，所以 state_dict 的 key 不变，全局形状可复原 |
| 名字对不上时 | **报错**（`TPConfigurationError`） | 实测：`tp_size=2` 配普通 `nn.Sequential` 时参数数不变、**无任何提示**——每个 rank 拿完整副本各训各的。现在要么切分要么报错 |
| 序列并行 | 自研 style（`_sharded_norm_style`），**不是** torch 的 `SequenceParallel` | torch 的 `SequenceParallel` **假定输入已经是本 rank 的序列切片**，只做标注（`from_local(..., run_check=False)`）。喂它一个复制张量不会切分，只会把全局序列长度标成 `world_size` 倍——实测 (2,4,8) 的输入变成了全局 (2,8,8) 的 DTensor，**什么都没报**，直到下一个模块的 `view` 失败并抛出与 SP 无关的 `Sharding propagation failed`。torch 自己的 Llama 例子能work是因为 embedding 就吐出序列分片、整条残差流都是分片的——那是模型的性质，框架没法给任意 `nn.Module` 装上 |
| 序列分片的传播 | 写成 `Replicate → Shard` 的布局迁移 | 手写 `chunk` 取本地切片是**静默错的**：chunk 的反向只给每个 rank 自己那一片的贡献，于是复制输入的梯度每 rank 都只填了一半——实测输入梯度误差 4.8e-03 / 7.0e-03，而正确值是 9.3e-10。写成布局迁移后，DTensor 的 autograd 自动给出对应的 all-gather |
| 复制参数的梯度归约 | DTensor 自动做 | 旧实现靠 `register_hook(all_reduce_gradient)` 手工归约，且去掉它副本会漂移（旧的多卡反证测过）。现在参数是 `Replicate` DTensor，DTensor 传播 Partial 梯度并在 autograd 里归约；把参数换成普通张量会**直接报错**（`got mixed torch.Tensor and DTensor`），不再有「静默漂移」这一档 |

**`sp_backend` 的 `ulysses` 与 `megatron` 在生产路径上没有区别**：`parallelize` 只按「非 none」启用 norm 的 SP；
两者的差异只在显式使用 `UlyssesAttention` 的地方（`examples/tp_sp_train`、`parallel_matrix`）。
这是「声明了但没接线」的一处，记录在案。

### L3 策略层 / L4 编排层 / L5 接口层

`trainer/` 是门面：**它直接持有全部状态**（`config` / `model` / `optimizer` /
`scaler` / `loss_fn` / `global_step` / `history` / `offload` / `overlap`），
行为委托给同级模块的自由函数。这不是风格问题——测试会直接写
`trainer.loss_fn = ...`，把状态代理到 session 对象会让这类赋值**静默失效**，
而失败会表现为数值不对而不是 AttributeError。`tests/unit/test_trainer_contract.py`
钉住了这条契约。

## 2. 流水线并行：一份实现

`parallel/pp_schedule.py` 是**唯一的**调度实现。`PipelineStage`
（`distributed_model.py`）只做委托，它保留的只有 `pp_size <= 1` 的快捷路径
（语义与调度的 `_run_local` 不同）。

| 类 | 角色 |
|---|---|
| `GPipeSchedule` | 全部前向 → 全部反向，激活保存在列表里 |
| `OneFOneBSchedule` | warmup / 稳态 / cooldown，异步发送 + 有界 FIFO |

**接收方式不是两套算法，而是同一个算法的一维参数**：

- 调用方已经知道邻居张量 spec（协议模拟器、显式 stage plan）→ 传 `input_specs`，走静态接收，带校验
- 生产路径在上游 header 到达前不知道形状 → 传 `None`，走动态接收，用 header 带来的 spec

`_recv_forward_any(spec_or_None)` / `_recv_backward_any(...)` 封装这一维。

**为什么不用 `torch.distributed.pipelining`（Stage D 的结论）**：它的初始化握手
（`pipelining/stage.py` 的 `_get_init_p2p_neighbors_ops`）用 `torch.zeros(1)` 收、
用 `torch.tensor(stage_index)` 发——float32 的 4 字节对 int64 的 8 字节，Gloo 的 UV
传输按字节校验，**直接 abort 进程且没有 Python 异常**。那个握手是「哑」的（作用是
预热通信器，由 NCCL 多机 hang 引入），把两端 dtype 改成一致后，PP=2 端到端跑通且
梯度与单进程逐位相同。**但迁移仍然没做**：修复要靠 monkeypatch torch 私有方法，而
本机能验证的收益是零（现有自研 PP 同样是 `0.000e+00`）。细节与对照实验见
`代码审计报告.md` 的 Stage D 一节。

**字符串/对象二元约定已消除**：`config.parallel.pp_schedule` 存名字，
`pp_schedule.build_schedule(name, ...)` 是唯一把名字变成对象的地方，
`PipelineStage` 是它唯一的调用方。

## 3. 校验在三处，各司其职

| 位置 | 负责 |
|---|---|
| `config/schema.py` | 每个配置**自身**的不变量（类型、范围、自洽） |
| `capability.validate_combinations` | **跨配置**规则（`dp_size>1` 需要 FSDP、microbatch interleave 拒绝 PP……） |
| `capability.validate_capabilities` | 公开入口：先 schema，再组合 |

`Trainer.__init__` 只调 `validate_capabilities` 一次。
`tests/unit/test_config.py` 会**数调用次数**——多校验一次就会失败。

**第四处校验在第二层，校验的是模型而不是配置**：`Trainer.__init__` 在
`dp_size>1` 时要求模型能推迟梯度归约（`parallel.fsdp.supports_gradient_sync`：
FSDP1/DDP 的 `no_sync`，或 FSDP2 的 `set_requires_gradient_sync`）。这条守的是
「配置说 FSDP 已启用，但交给我的模型根本没被切分」——那种情况下每个 rank 会各
自用自己的梯度更新，不报错，只是收敛到不同的模型。

### FSDP1 的字段没有对应物，已删除

`FSDPConfig` 现在只有 `enabled` 与 `mixed_precision` 两个字段。原先的
`sharding`（FSDP2 只有一种切分方式）、`limit_all_gathers`、`forward_prefetch`
（FSDP1 的调度开关，FSDP2 无对应物）、`execution_trace_complete`（只为给
`forward_prefetch` 把关而存在）、`cpu_offload`（改成抛错的惰性字段，指向真正
实现的 `FrameworkConfig.offload`）全部删除。删掉的理由不是精简，而是**它们到不了
任何地方**：配置可以设成 true，训练照旧既不分片也不预取，没有任何信号。

## 4. 能力边界：声明与实现的差距

`capability_matrix()` 里每条都带一句如实的理由。以下几条**已实现但未接线**，
读代码时不要误以为模型路径会走它：

| 能力 | 状态 |
|---|---|
| `kernel_eager_fallback` / `flash_attention` / `fused_*` | `kernels/` 自成一体，**没有任何生产调用方**；`parallel/sp_ulysses.py` 直接调 `torch.nn.functional.scaled_dot_product_attention` |
| `parameter_prefetch` | `ParameterOffloader.prefetch_async` **无任何调用方**（连测试都没有）；`Trainer` 只调 `fetch`/`release` |
| 高级 overlap 开关 | **仅拒绝用**：打开它们不启用功能，只让启动阶段拒绝真正无法工作的组合。删掉它们等于悄悄放宽可接受配置空间 |
| `planning_report` | `suggest_plan` 是库入口；CLI 的 `dry-run` 报告配置与能力矩阵，**不是**计划 |

## 5. 检查点：两种格式，两个入口

**它们是两个入口，不是一个函数按配置改行为** —— 两种格式写出的 checkpoint
互不可读，所以选择必须是显式调用。

| 入口 | 格式 | 语义 | 适用 |
|---|---|---|---|
| `Trainer.save_checkpoint` / `load_checkpoint` | 每 rank 一个 `rank_state.pt` | **每 rank 一份完整副本**。`save` 不含集合通信，每个 rank 写自己的路径 | 默认；中文档以下最简单可靠 |
| `Trainer.save_sharded` / `load_sharded` | `torch.distributed.checkpoint` | **真分片**，集合通信，**所有 rank 必须传同一路径** | 模型大到 N 份副本不划算时 |

分片路径带 optimizer 状态（用 AdamW 验证过 `optimizer.state` 非空）与
`global_step`/`optimizer_step`，所以是可续训的。

### 分片路径覆盖哪些轴，以及为什么

**TP 与 PP 都能存，但修好的原因不一样**，这一点值得单独写清楚，因为两者
都曾经**静默损坏**过（save 和 load 都报成功）：

| 轴 | 靠什么成立 | 写错的症状 |
|---|---|---|
| **TP** | 参数是 `DTensor`（Stage B）。DCP 因此知道 `q_proj.weight` 是**一个**张量、被若干 rank 分片持有 | 旧的自研 TP 参数是「装着分片的普通 Parameter」，每个 rank 把自己的当完整张量写进同一个 key，最后写入者胜出 |
| **PP** | `checkpointing._stage_prefix`：`pp_size>1` 时把 key 加上 `stage.<id>.` 前缀 | `split_sequential` 给**每个 stage** 各自的 `nn.Sequential`，于是 stage 0 和 stage 1 都把孩子命名成 `0` —— 同一个 key 下是两个不同的张量。实测 pp=2 往返后两个 rank 拿到的是**同一个**张量、且都不是自己的，`max\|dW\| = 6.4e-01`；加上前缀后是 `0.000e+00` |

前缀只在 `pp_size>1` 时加，这是**key 唯一性的要求**而不是配置开关：只有一个
stage 时 `0.weight` 本来就是唯一的，所以单 stage 的 checkpoint 布局没有变化。

**重分片（换 world size / 换 TP 布局加载）是可用的**，而不再只是「拒绝」：
分片 checkpoint 里张量带全局描述，所以 DCP 能把整个 checkpoint 交给一个
**没有进程组**的单进程读取（`no_dist=True`）——这同时换了 world size 和 TP 布局。
实测 tp=2 存的 checkpoint 在单进程里读进一个 dense 模型，`max|diff| = 0.000e+00`，
形状是全局的 `(8, 8)` 而不是某个 rank 的 `(4, 8)`。

**库层面另有两条入口**：`CheckpointConverter.convert` +
`ModelLoader.load_for_rank`（manifest + 每 rank 一个文件）。它们只按 **TP 轴**切分；
`dp_size` 是**复制**而非切分，且调用方要自己算 `(pp,tp,dp)` 坐标。

`pp_size>1` 需要的 `stage_assignment`（张量名 → stage）不再要调用方手写：
`parallel.pp_shapes.stage_assignment(model, pp_size)` 跑**训练路径用的同一个**
`split_sequential` 得出，所以 checkpoint 与训练不会对「某一层去了哪个 stage」有分歧。
它能这样做的前提是 `PipelineSequence` 保留了原名（见 §2）。

**已实测的读取行为**（tp=2、`Linear(64,64)`）：`load_sharded` 时 rank 0 读
`q_proj.weight` 的 offset `(0,0)`、rank 1 读 `(32,0)`——**同一文件的不同区间**，
每个 rank 只读自己那一片；`o_proj` 按 dim 1 切（`(0,0)` vs `(0,32)`），
复制参数两边都读。`load_for_rank` 同理，并返回 `bytes_read` 供诊断。
**没有任何一条路径是「rank0 读完整模型再广播」。**

### 实测：分片路径支持哪些并行策略组合

下表是**实跑出来的**（每条都训练 2 步 → 集体保存 → 重建 → 加载 → 比对，全部
`max|dW| = 0.0e+00`）。回归网是 `tests/unit/test_multirank_gloo.py` 的
`test_sharded_checkpoint_round_trips_axis_combinations`，参数化覆盖下列组合。

| world | 组合 | 结果 |
|---|---|---|
| 2 | `dp=2` / `pp=2` / `tp=2` / `tp+sp` | ✅ |
| 4 | `dp=4` / `pp=4` / `tp=4` | ✅ |
| 4 | `dp=2,tp=2` / `dp=2,pp=2` / `tp=4+sp` / `dp=2,tp=2+sp` | ✅ |
| 4 | `tp=2,pp=2` | ✅ |
| 8 | **`dp=2,tp=2,pp=2`** ／ 再加 `+sp` | ✅ |

**`pp` 与 `tp` 曾经完全无法组合**，根因在 checkpoint 之前：`split_sequential` 把每个
stage 的子模块包进各自的 `nn.Sequential`，于是**每个 stage 的模块名都变成 `0, 1, …`**，
按后缀名匹配的 TP plan 一个都找不到。现在 `split_sequential` 用 `PipelineSequence`
（`parallel/pp_shapes.py`）**保留原名**，一并解决了两个问题：

- TP plan 能在 stage 上找到 `q_proj`/`o_proj` 等 → **pp 与 tp 可以组合**；
- 各 stage 的 checkpoint key 不再撞名 → `checkpointing._stage_prefix` 这个绕行**已删除**。

**但组合有一条结构约束**：每个 stage 内部必须有完整的 col→row 配对。column 投影输出的是
分片激活，只有配对的 row 能消费它；跨 PP 边界传的是完整张量，对端的 row 会把它当成
分片。实测把 column 和它的 row 分到不同 stage 时，`fit` 会**死锁**（Gloo recv 超时），
而不是报形状错。每个 stage 自洽时（例如每个 top-level child 就是一个 norm+col+row 单元），
四轴全开逐位正确。

**仍然存在的限制**：`CheckpointManager.allow_world_size_change` 只跳过 world size
检查，那条路径（`save`/`load`，每 rank 一个文件）**没有**重分片实现。重分片能用的是
**分片**路径，不是这条。

## 6. 随机性：seed 不按 rank 偏移

`Runtime(seed=...)` 给**所有 rank 同一个** seed（`runtime.py` 的 `seed_everything(seed)`）。
曾经是 `seed + rank`，看起来像「让各 rank 数据不同」的常规手法，但这里 seed 的是**全局
RNG**，而调用方正是从全局 RNG 取模型初始化：

- 本仓所有示例、以及 `Trainer.__init__` 自己的 docstring 都推荐「先建 `Runtime` 再建模型」，
  于是每个 rank 建出**不同的模型**；
- 实测 world=2：rank 0 的 `torch.initial_seed()` 是 1234、rank 1 是 1235，
  「同一个」模型在一步训练之前就差 `max|dW| = 6.9e-01`；
- 两件事把它藏住了：**TP** 的 `distribute_tensor` 从 `src_data_rank` 广播参数，直接覆盖了
  差异；**FSDP** 的 all-gather 把两个 rank 各一半拼成一个「看起来正常」的模型。
  **PP** 两样都没有，所以是它暴露出来的。

数据分片本来就由调用方负责（`seed_everything` 的 docstring 一直这么写），所以按 rank
偏移没有换来任何东西。rank 0 的行为不变，单进程完全不受影响。

## 7. 可选 torch

`import aitrainer` 在**没有 torch** 的机器上必须成功——那是只做配置校验、
拓扑检查、规划的场景。这条性质由 `tests/unit/test_torch_optional.py` 钉住：
它在导入机制层屏蔽 `torch`，然后断言 `__all__` 里每个名字都能解析。

所有可选导入的**策略**收敛在 `core/torch.py`；各调用点的**错误域**保持原样
（`P2PError`、`FSDPConfigurationError`、`ProcessGroupError` 各有所指）。
