# 使用指南：把你的模型接上并行训练

> 这份指南回答一个问题：**拿一个自己的模型来，要改多少东西才能用上各种并行策略。**
>
> 所有数字都是本机（CPU / Gloo，macOS）实测的，跑法写在每一节里。**没有实测支撑的说法会明确标注**，
> 这个项目反复证明过：没跑过的断言里藏着缺陷。

## 0. 环境准备与五分钟跑通

### 0.1 依赖

**硬依赖只有 torch 一个。** 这是刻意的：框架不依赖 deepspeed / megatron / transformers，
`src/` 里第三方 import 只有 `torch`，所以把它接上你的模型不需要额外装一整套生态。

| | 要求 | 说明 |
|---|---|---|
| Python | **>= 3.10** | `pyproject.toml` 的 `requires-python` |
| torch | **>= 2.1** | 唯一运行期依赖，`pip install` 会自动带上 |
| 开发/测试 | pytest, ruff, mypy, import-linter | `pip install -e ".[dev]"` 才装，训练用不到 |
| 可选加速库 | `flash_attn`、`transformer_engine`、`triton`、`safetensors` | **框架只探测、不要求**（`capability.py:169`）。装了会反映在 `capability_matrix()` 里，不装不影响任何路径 |

### 0.2 真实 GPU 服务器需要什么

| | 要求 | 为什么 |
|---|---|---|
| GPU | NVIDIA，多卡需要 NCCL | PyTorch 的 Linux wheel **自带 CUDA runtime 与 NCCL**，所以系统里**不需要装 CUDA toolkit**，只需要**驱动** |
| 驱动 | `nvidia-smi` 报告的 CUDA 版本 **≥ wheel 的版本** | `cu126` 的 wheel 装在只支持 CUDA 12.4 的驱动上会**在 import 时**失败，而不是在安装时 —— 装完才发现 |
| 系统 | Linux | macOS 上无 CUDA，只能跑 CPU/Gloo |
| 多机 | 各节点间 NCCL 可达、`MASTER_ADDR`/`MASTER_PORT` 通 | 本仓库的多机路径没有专门验证过 |

**NCCL 是分水岭**：它决定了哪些能力真的可用。

| 能力 | CPU / Gloo | CUDA / NCCL |
|---|---|---|
| FSDP、TP、SP、PP、检查点 | ✓ 本机全部实测过 | ✓ |
| 多 rank 训练 | ✓ | ✓ |
| **Ulysses**（`UlyssesAttention` / `distributed_attention`）| ✗ | ✓ |

Ulysses 用的是 `all_to_all`，**Gloo 没有它的实现**，所以在 CPU 上无论怎么配都会
`RuntimeError: Backend gloo does not support alltoall`。这也是 `sp_backend='ulysses'`
在配置校验期就被拒绝的原因（详见 README 的 SP 一节）。

**另有一处 CPU 限制**：DTensor 在 CPU 上没有 `scaled_dot_product_attention` 的分片策略，
所以 attention 需要一次本地往返（§3.2b）。CUDA 上可能不需要 —— **未实测**，
已列入 `docs/GPU验证清单.md` 的 C5。

### 0.3 一键创建 `.venv`

在仓库根目录创建 `.venv`：

```bash
cd /path/to/aiTrainer
bash scripts/create_venv.sh                 # torch 走 PyPI 默认轮子（Linux 上是 CUDA 版）
```

| 参数 | 用途 |
|---|---|
| `--cuda cu126` | 指定 CUDA wheel 线（要和驱动对得上，见 §0.2）|
| `--cpu` | 只装 CPU 轮子（下载小得多，适合笔记本）|
| `--force` | 重建已存在的 `.venv`（会先删掉整个目录）|
| `--no-smoke` | 跳过末尾的 3 步训练冒烟检查 |

脚本做四件事：找一个 >= 3.10 的解释器 → 建 `.venv` → 装 torch（指定索引时用对应索引）
→ `pip install -e ".[dev]"` → 打印实际装到的版本与 CUDA/NCCL 状态 → 跑一次单进程训练。
**装完自己会证明能训练**，不用你另外猜。

装完后 `source .venv/bin/activate`，或者直接用 `.venv/bin/python`。

> 脚本**不会**替你起多 rank 进程 —— 本仓库所有脚本都不自己起进程，原因见
> `examples/llama_shaped/train.py` 的 docstring。多 rank 的启动命令见 §0.4。

### 0.4 五分钟跑通

```bash
cd /path/to/aiTrainer
PY=.venv/bin/python                  # 由 scripts/create_venv.sh 创建（§0.3）

# 单进程，不需要进程组
$PY examples/llama_shaped/train.py --strategy single
```

实测输出：

```
rank 0/1 stage=0 steps=3 loss 4.392560 -> 4.332551 took 0.02s
single: rank0 loss 4.392560 -> 4.332551 steps=3 rank0_params=45,344 took 0.02s
```

这就是后面所有策略的**基准**。多 rank 由你自己起进程（脚本永不自己起进程 —— 原因见
`examples/llama_shaped/train.py` 的 docstring，那里记着两次把机器拖垮的事故）：

```bash
for r in 0 1; do MASTER_ADDR=127.0.0.1 MASTER_PORT=29500 WORLD_SIZE=2 RANK=$r \
    $PY examples/llama_shaped/train.py --strategy fsdp --world 2 & done; wait
```

或者用现成的脚本一次跑完（前台运行，卡住 Ctrl-C 即可）：

```bash
PY=$PY bash scripts/check_llama_shaped.sh              # 全部策略
PY=$PY bash scripts/check_llama_shaped.sh tp pp        # 只跑指定几条
```

`--world` 是**声明**你要起几个进程，不是让它去起；它和 `WORLD_SIZE` 不一致会被拒绝，
而不是在集合通信里挂住。

## 1. 决策表：我该开哪个轴

| 你的目标 | 开什么 | 模型必须改什么 | 代价（结构性，非实测）|
|---|---|---|---|
| 单卡装不下，想切参数 | `dp_size>1` + `fsdp.enabled` | **无** | 每层 all-gather + reduce-scatter |
| 单层太大，切不动 | `tp_size>1` | 层名要命中 plan 后缀；**attention 要改一处** | 每个行投影一次 all-reduce |
| 激活显存太大 | `tp_size>1` + `sp_backend` | 无（norm 按类型匹配）| 每个 norm 一次 reduce-scatter/all-gather |
| 层数太多，单卡放不下整模型 | `pp_size>1` | 模型 forward 是链式，或提供 `execution_order` | **气泡**，见 §4 |
| 都要 | 组合（见 §3.5）| 取并集 | 取并集 |

**轴必须相乘等于 world size**，否则配置校验期直接拒绝（不是近似）。

## 2. 真实案例：`examples/llama_shaped/`

模型按 HuggingFace 的 Llama 形状写的，**零额外依赖**（不需要 `transformers`），
但三个结构特征与真实 HF 模型一致，而这三个特征正好决定了每种策略要改什么：

| 结构 | 对应的策略要求 |
|---|---|
| 投影叫 `q_proj` / `k_proj` / `v_proj` / `o_proj` / `gate_proj` / `up_proj` / `down_proj` | **TP** —— 默认 plan 按这些名字匹配 |
| norm 是 `nn.RMSNorm` | **SP** —— 按**类型**匹配，无命名要求 |
| 层嵌在 `model.layers` 里一层深，`lm_head` 与 `model` 平级 | **PP** —— 顶层切分切不到真正的层 |

规模：`vocab 64 / hidden 32 / ffn 64 / 4 层 / 4 头`，**45,344 参数**。
故意做得极小 —— 每个多 rank 进程都要各自加载一份 torch，模型小才让 4 rank 运行不成为负担。

### 实测结果（全部在本机跑过）

同 seed、同数据、3 步。所有策略的 loss 都应与单卡基准**一致**，因为 `fit` 收到普通 list 时
**不按 DP rank 分片数据**（见 §4.1），每个 rank 看到相同的样本。

| 策略 | world | loss（首 → 末）| rank0 参数量 | 耗时 |
|---|---|---|---|---|
| `single` | 1 | `4.392560 -> 4.332551` | 45,344 | 0.02s |
| `tp` | 2 | 同基准 | 45,344 | 0.09s |
| `tp_sp` | 2 | 同基准 | 45,344 | 0.11s |
| `pp` | 2 | rank1 同基准；**rank0 为 `0.000000`**（见下）| 32,960（stage 0）| 0.04s |
| `fsdp` | 2 | 同基准 | 45,344 | 0.04s |
| `dp2_tp2_sp` | 4 | 同基准（4 个 rank 全部）| 45,344 | 0.14s |

**`pp` 的两个需要解释的地方**：

- **rank 0 的 loss 是 `0.000000`，这是设计行为**：非末段 stage 没有 loss，
  `run_pipeline_step` 里回落到 `0.0`。**注意这意味着 `0.0` 和"真的收敛到 0"无法区分** ——
  PP 下只有末段 stage 的 loss 有意义。
- **参数量 32,960 恰好等于切分数学**：每层 `2×32`（两个 RMSNorm）+ `4×32×32`（q/k/v/o）
  + `3×32×64`（gate/up/down）= 10,304；stage 0 = embed 2,048 + 3 层 = **32,960**；
  stage 1 = 1 层 + norm + lm_head = 12,384；合计 45,344，与单卡一致。
  这证明**参数确实按层切开了**，而不是整个 trunk 留在 stage 0。

**参数量怎么读**：TP 下报的是**逻辑尺寸**（参数是 `DTensor`，`numel()` 给的是全局形状），
所以和单卡相同；PP 下才是真的更少（stage 只持有子集）。

## 3. 逐轴说明

### 3.1 FSDP —— 零侵入

```python
config = FrameworkConfig.from_dict({
    "parallel": {"dp_size": 2}, "fsdp": {"enabled": True}})
```

**模型要改什么：什么都不用改。** 按参数包装，不关心模型结构、命名或前向。

- 必须显式 `fsdp.enabled=True`，`dp_size>1` 不会自动开启
- 多 rank 需要已初始化的进程组
- 每个 rank 都要能调到 `set_requires_gradient_sync`（FSDP2 的名字）或 `no_sync`

### 3.2 TP —— 命名耦合，且 attention 要改一处

```python
config = FrameworkConfig.from_dict({"parallel": {"tp_size": 2}})
```

**模型要改什么：**

**（a）投影层名要命中默认 plan 的后缀。** 列：`q_proj`、`k_proj`、`v_proj`、`gate_proj`、
`up_proj`、`linear1`；行：`o_proj`、`out_proj`、`down_proj`、`linear2`。匹配的是**叶名**，
所以 `layer_0.self_attn.q_proj` 也能命中。

名字对不上时**不是静默不切** —— `tp_size>1` 且 plan 一个模块都没匹配到会直接拒绝：

```
TPConfigurationError: tp_size=2 but the plan names no module to shard, so the
model would run as independent full replicas with no collectives and no error.
```

要么改名，要么传自己的 plan（`parallelize(..., tp_plan=YourPlan())`，鸭子类型，实现
`role`/`styles`/`validate_dimensions`/`partition_dims`）。

**（b）`scaled_dot_product_attention` 要包一层。** 这是唯一一处模型的实质改动，原因是
**DTensor 没有这个算子的分片策略**：

```
NotImplementedError: Operator aten._scaled_dot_product_flash_attention_for_cpu.default
does not have a sharding strategy registered.
```

修法是通用的本地往返，**不需要知道 `tp_size`**（mesh 和 placement 从张量自己身上读）：

```python
def _per_head(query, key, value):
    if not hasattr(query, "to_local"):
        return torch.nn.functional.scaled_dot_product_attention(query, key, value)
    from torch.distributed.tensor import DTensor, Shard
    attended = torch.nn.functional.scaled_dot_product_attention(
        query.to_local(), key.to_local(), value.to_local())
    return DTensor.from_local(attended, query.device_mesh, [Shard(1)])
```

为什么这是**精确的**而不是近似：分片分的就是 **head 轴**，每个 rank 持有**完整的 head**，
而 attention 逐 head 独立。框架没法替你兜底，因为"按 rank 分别算等于整体算"这个事实
只有模型自己知道。

> **`Shard(1)` 那个数字要数清楚。** 在例子里，投影输出是 `(batch, length, heads, head_dim)`
> 分片在 dim 2，而 `Attention.forward` 先做了 `transpose(1,2)` 才调用它，所以进来时 head 轴在
> **dim 1**。**写错了不会报错** —— 它会把序列轴标成分片轴，产出一个"描述了没人算过的张量"的
> DTensor。

其余一行都不用改：分片被限制在 attention / MLP 区域内，残差流永远看不见它。

### 3.3 SP —— 零命名，按类型匹配

```python
config = FrameworkConfig.from_dict({
    "parallel": {"tp_size": 2, "sp_backend": "megatron"}})
```

`sp_backend` 是**开关**不是选择器 —— 本框架只有一种实现。且它**要求 `tp_size>1`**。

**模型要改什么：什么都不用改**（前提是 norm 是我们认识的类型）。

- 目前认识 `nn.LayerNorm` 和 `nn.RMSNorm`（后者是 Llama 用的）
- **不认识的 norm 类型会被拒绝**，不会静默空转：

  ```
  TPConfigurationError: parallel.sp_backend is set but this model contains no norm
  the sequence-parallel style can shard (it knows LayerNorm, RMSNorm) ...
  ```

  这条守卫是后加的。在它之前，一个用自定义 norm 的模型会**带着 SP 配置跑完而 SP 完全没生效**，
  **loss 曲线看不出来**（SP 是激活布局优化，不影响数值）。
- 想支持自己的 norm 类型：把它加进 `parallel.tp.sequence_parallel_types()`。样式本身与具体
  norm 无关 —— 它切的是**序列**轴，norm 自己的轴（最后一维）在每个 rank 上都是完整的，
  所以任何在 hidden 维归一的模块都适用。
- **dropout 必须放在 norm 之外**（框架自动如此）。放进区域内，每个 rank 会用序列第一块的
  mask，实测与单进程差 `9.6e-01`。

### 3.4 PP —— 需要 `execution_order`

```python
config = FrameworkConfig.from_dict({"parallel": {
    "pp_size": 2, "pp_schedule": "gpipe", "num_microbatches": 2}})
```

**模型要改什么：取决于 `forward` 是不是"直接子模块的链"。**

- **是链**（`nn.Sequential` 那种）：什么都不用改。
- **不是链**（HuggingFace 形状：层嵌在 `model.layers` 里）：**必须提供 `execution_order`**。

不提供会被**拒绝**（而不是切错）：

```
PipelineShapeError: pp_size=2 cannot split ['model'] -- this module defines no
forward, so a pipeline stage holding it could never run. ...
```

判据是**可证明的**而非启发式：`PipelineSequence` 逐个调用子模块，没有 `forward` 的孩子
（裸 `nn.Module`、`nn.ModuleList`）无论怎么分配到 stage 都跑不起来。

`execution_order` 的写法（`examples/llama_shaped/model.py` 里有一份可抄）：

```python
def llama_execution_order(model):
    return [("embed_tokens", model.model.embed_tokens),
            *[(f"layer_{i}", layer) for i, layer in enumerate(model.model.layers)],
            ("norm", model.model.norm),
            ("lm_head", model.lm_head)]

model = parallelize(raw, config=config, runtime=runtime,
                    execution_order=llama_execution_order)
```

必须包含 **glue**（embedding、最终 norm、head），因为 stage 是一个可调用链。
名字**不能带点**（`PipelineSequence` 用 `add_module` 注册，它拒绝 `"."`），带点的写法会被
明确挡下并提示，而不是抛 `nn.Module` 内部的 `KeyError`。

**已知局限（刻意不修）**：如果那个容器**自己定义了可用的 `forward`**（HF 的 `LlamaModel`
就是），框架无法把它和"有意切成两段"区分开，因此不拒绝 —— 结果是整个 trunk 落在 stage 0。
参数计数会显示这一点，`execution_order` 是解法，但没有自动检查会拦它。要拦只能靠猜模型结构，
而猜错会拒绝能工作的配置。

### 3.5 组合

轴相乘等于 world size 即可，例如 4 rank 的全轴：

```python
config = FrameworkConfig.from_dict({"parallel": {
    "dp_size": 2, "tp_size": 2, "pp_size": 1, "sp_backend": "megatron"}})
```

组合时**取各轴要求的并集**：命名（TP）+ `execution_order`（PP，如果需要）。

分片 checkpoint（`save_sharded` / `load_sharded`）在任意组合下都应当往返无损，
覆盖情况见 `scripts/verify_parallel.py`。

## 4. 会变慢的地方

> **本机没有测到任何有意义的效率数字。** 模型 45k 参数、跑 3 步，上表那些 0.02–0.14s 由进程
> 启动主导，**不能**用来比较各策略的效率。这一节说的都是**结构性代价**（设计使然），
> 真实数字必须在 GPU 上测，见 `docs/GPU验证清单.md` 的 C 节。

### 4.1 DP 下直接把 list 传给 `fit`，等于纯开销

`Trainer.fit` **不按 DP rank 分片数据**。给普通 list 时，每个 rank 训练**完全相同的样本**，
于是梯度相同，而 reduce-scatter/all-gather 是在归约一份本来就相同的值 —— **计算是冗余的，
通信是白付的**。

想让 DP 有收益，必须提供会分片的 `DataProvider`（`train_dataloader(dp_group=...)`）。
这也是本指南各策略 loss 能一致的原因：数据相同，归约是恒等。

### 4.2 PP 的气泡

`pp_size` 段流水线，首个 micro-batch 填满前和排空前，部分 stage 是空闲的。
段数越多气泡越大。用 `num_microbatches` 摊薄，但 1F1B 需要
`num_microbatches >= pp_size`。

### 4.3 TP 的每个行投影一次 all-reduce

行投影（`o_proj`/`down_proj`）的输出需要跨 TP 组 all-reduce 才能回到完整张量。
层数 × 每层行投影数，就是每步的 all-reduce 次数。这是 TP 的固有代价，
换来的是每 rank 的参数量和激活都降到 `1/tp_size`。

### 4.4 SP 的每个 norm 一次规约

每个被 SP 包住的 norm 有一次 reduce-scatter（进）和 all-gather（出）。
收益是 norm 的激活从全局序列降到 `1/tp_size`。

### 4.5 梯度累积下的额外集合通信

梯度累积窗口内，参数梯度按窗口边界归约；SP 下 norm 参数的 `Partial` 归约在
**每个 optimizer step** 做一次（不是每个 micro-batch）。

## 5. 报错 → 原因 → 怎么改

| 报错 | 原因 | 怎么改 |
|---|---|---|
| `TPConfigurationError: the plan names no module to shard` | 层名没命中 plan 后缀 | 改名，或传 `tp_plan=` |
| `TPConfigurationError: ... contains no torch.nn.LayerNorm` | norm 类型不认识 | 加进 `sequence_parallel_types()`，或 `sp_backend="none"` |
| `NotImplementedError: ... does not have a sharding strategy registered` | DTensor 没有该算子的分片策略 | 算子前后做本地往返（§3.2b），用张量自己的 `device_mesh` |
| `RuntimeError: got mixed torch.Tensor and DTensor` | 残差流（普通张量）里混进了 `DTensor` | 不应再出现；若出现说明 `keep_placements` 的作用域被改错了 |
| `shape '[2, 8, 4, 8]' is invalid for input of size 256` | 拿着**分片后**的本地张量按全局尺寸重排 | 同上：确认拿到的是 `DTensor`（有 `placements`）而不是普通张量 |
| `PipelineShapeError: ... defines no forward` | 模型是嵌套的，PP 切不到真正的层 | 提供 `execution_order`（§3.4）|
| `PipelineShapeError: ... must not contain '.'` | `execution_order` 的名字带了点 | 用无点的名字，如 `layer_0` |
| `ModuleNotFoundError: No module named 'aitrainer'` | 直接跑 `scripts/verify_parallel.py` 但没设 `PYTHONPATH` | 加 `PYTHONPATH=src` |
| `--world N but WORLD_SIZE=M` | 声明的进程数与实际不符 | 按提示把两者对齐 |

## 6. 本机验证了什么 / 没验证什么

**已在 CPU / Gloo 本机实测**（`270 passed`、ruff 84、3 契约之外的部分）：

- 六种策略的 loss 与单卡基准一致（§2 表）
- PP 的参数确实按层切开（32,960 + 12,384 = 45,344）
