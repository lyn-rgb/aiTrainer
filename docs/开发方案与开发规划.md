## 1. 文档目标和执行规则

### 1.1 目标

实现一个模型无关、训练策略可插拔、分布式能力可验证的 PyTorch 训练基础框架，按以下路径逐步交付：

```text
单卡基线
  → FSDP/DP
  → Megatron 风格 TP
  → Ulysses/Megatron 风格 SP
  → PP（GPipe/1F1B）
  → CPU Offload
  → 计算-通信重叠
  → Kernel/Memory/Topology 优化
  → 高级计算-通信流水和资源调度
```

### 1.2 规范性说明

- 本文的“必须”表示该批次的交付条件；“可选”表示不得阻塞当前批次；“禁止”表示不得以隐式降级替代。
- 每个批次必须先完成正确性测试，再开启异步通信、预取、offload、compile 等性能开关。
- 每个新能力都必须补齐配置校验、最小示例、单元测试、分布式测试、性能基线和回退路径。
- 参考代码只用于提炼算法和接口语义，不能直接导入 `references/` 下的包；接入前必须完成许可证和版本审查。
- 默认安装只包含 Python 标准库、项目锁定版本的 PyTorch/torch.distributed/DCP 及 CUDA/NCCL 运行时；第三方 kernel、模型库和通信框架均不得作为核心依赖。
- 开发不得遗留半成品：一旦某开发项进入编码阶段，就必须完整实现该项在本批次定义的正常路径、错误路径、资源清理、配置接线和 fallback；验证可以随后进行，但实现本身不能以 TODO、空函数或临时逻辑收尾。
- 尚不具备实现条件的能力应整体保留在后续批次并保持“未开始/已阻塞”，不得提前暴露不可用的公共 API、配置开关或假实现。

### 1.3 当前项目状态

当前仓库已完成批次 0～8 的代码交付，组合入口已接入 PP → TP/SP → FSDP(DP group) 顺序；工程仍保留“无参考仓库运行”检查，尚未通过硬件环境验证的能力不得标记为“已完成”。

## 2. 目标架构和稳定边界

### 2.1 分层架构

```text
应用层
  ModelAdapter / ModelSpec / ParallelPlan / DataProvider / LossFn / OptimizerFactory
                                  │
框架层
  Trainer / DistributedModel / Parallelizer / CheckpointManager
                                  │
并行层
  TP / SP / PP / FSDP / Offload / Overlap / KernelBackend
                                  │
运行时层
  Runtime / DeviceMeshManager / TopologyPlanner / ProcessGroups
                                  │
诊断层
  Config / CapabilityMatrix / MemoryPlanner / Metrics / Profiler / Diagnostics
```

### 2.2 三套必须冻结的契约

#### 布局契约

每个模块必须声明输入和输出布局，至少支持：

```text
replicated       每个 rank 持有完整 tensor
partial          每个 rank 持有需要 reduce 的部分结果
sequence_sharded 按序列维度分片
head_sharded     按 attention head 维度分片
hidden_sharded   按 hidden/linear 输入输出维度分片
```

布局对象至少包含：`shape`、`dtype`、`device`、`shard_dim`、`group`、`requires_grad`、`valid_lengths`。

#### 生命周期契约

参数、激活、梯度、通信 buffer 和 offload buffer 必须登记：

```text
owner → producer stream/event → consumer stream/event → last use → release/recycle
```

任何异步操作在 optimizer、checkpoint、异常退出和进程销毁前必须调用统一 `drain()`。

#### 能力契约

每项能力在当前环境中标记为：

```text
stable        已通过单元、分布式和恢复测试，可作为默认能力
experimental  可显式开启，但必须输出警告和回退方案
unsupported   启动阶段拒绝，不能运行中静默降级
```

## 4. 详细开发内容

### 4.1 配置、预设和能力矩阵

#### 代码位置

- `src/aitrainer/config.py`
- `src/aitrainer/presets.py`
- `src/aitrainer/capability.py`
- `src/aitrainer/diagnostics.py`

#### 开发内容

实现分层不可变配置：

```python
@dataclass(frozen=True)
class ParallelConfig:
    dp_size: int = 1
    tp_size: int = 1
    pp_size: int = 1
    sp_backend: Literal["none", "ulysses", "megatron"] = "none"
    pp_schedule: Literal["none", "gpipe", "1f1b"] = "none"
    num_microbatches: int = 1

@dataclass(frozen=True)
class PrecisionConfig:
    # 没有 param_dtype，也没有 reduce_dtype：
    #   参数存储 + FSDP 归约 dtype 由 FSDPConfig.mixed_precision.dtype 一个字段表达；
    #   param_dtype 从来没有消费者，reduce_dtype 的接线在 DTensor 迁移中被删除。
    #   两者都已从代码删除，并由 test_every_config_field_is_read_somewhere 守着。
    compute_dtype: torch.dtype = torch.bfloat16
    grad_dtype: torch.dtype = torch.float32
    optimizer_dtype: torch.dtype = torch.float32
    use_grad_scaler: bool | None = None

@dataclass(frozen=True)
class CompileConfig:
    enabled: bool = False
    mode: str = "default"
    fullgraph: bool = False
    dynamic: bool = False

@dataclass(frozen=True)
class FrameworkConfig:
    parallel: ParallelConfig
    precision: PrecisionConfig
    compile: CompileConfig
    # memory/offload/overlap/checkpoint 配置省略字段，按同样方式拆分
```

实现预设：

```python
ConfigPreset.single_gpu()
ConfigPreset.fsdp()
ConfigPreset.tp()
ConfigPreset.tp_fsdp()
ConfigPreset.memory_saving()
ConfigPreset.performance()
```

能力矩阵以 `(torch_version, cuda, backend, model_feature, parallel_combo)` 为 key，至少检查：

- TP + FSDP + DTensor；
- SP + compile；
- PP schedule + P2P overlap；
- activation offload + recompute；
- fp16 + PP loss scaling；
- FP8、FlashAttention、CPU optimizer 等 backend。

启动校验必须拒绝：world size 不匹配、维度不可整除、空 stage、micro-batch 数不足、未知 layout、重复 shard、共享参数处理缺失、未验证组合。

#### 参考内容

- 当前设计文档第 5 节：配置和启动校验、`FrameworkConfig`；
- `references/Megatron-LM/megatron/core/parallel_state.py`：`initialize_model_parallel`、TP/PP/DP group 构建和 rank 查询；
- `references/DeepSpeed/deepspeed/runtime/zero/offload_config.py`：offload device、buffer、pin memory、pipeline read/write 配置。

#### 验收标准

- 非法配置在初始化 process group 后、创建模型前报错；
- `validate` 输出完整展开配置、能力矩阵和 fallback；
- `dry-run` 不修改模型参数、optimizer、RNG 或 checkpoint；
- 预设和显式配置生成同一份可比较的最终配置。

### 4.2 Runtime、DeviceMesh 和硬件拓扑

#### 代码位置

- `src/aitrainer/runtime.py`
- `src/aitrainer/mesh.py`
- `src/aitrainer/topology.py`
- `src/aitrainer/parallel/groups.py`

#### 开发内容

1. `Runtime.start()` 初始化 process group、设置 `LOCAL_RANK`、设置 seed、注册退出清理。
2. `TopologyPlanner` 探测 GPU 名称、显存、PCI bus、NUMA、NVLink/NVSwitch 和节点网络。
3. 生成真实 `RankMapping`，记录每个 `(pp, dp, tp)` 坐标对应的 global rank。
4. 默认 TP 放在同一高速互联域；PP 尽量使用节点边界；DP/FSDP 使用剩余设备。
5. `DeviceMeshManager` 使用 rank mapping 创建命名 mesh，并暴露 `tp_group`、`sp_group`、`pp_group`、`dp_group`。
6. 提供 `inspect-topology`，输出文本和 JSON 两种格式。

建议接口：

```python
class TopologyPlanner(Protocol):
    def inspect(self) -> HardwareTopology: ...
    def plan(self, config: ParallelConfig) -> RankMapping: ...

class DeviceMeshManager:
    def initialize(self, mapping: RankMapping) -> None: ...
    def group(self, name: Literal["dp", "tp", "sp", "pp"]): ...
```

#### 参考内容

- `references/Megatron-LM/megatron/core/parallel_state.py`：正交 TP/PP/DP group、首尾 stage 和 next/prev rank；
- `references/Megatron-LM/megatron/core/transformer/pipeline_parallel_layer_layout.py`：pipeline layer layout 的思路；
- 当前设计文档第 3.2 节：拓扑规划和成本模型。

#### 边界

本批只做探测、显式 mapping 和校验，不做自动全局搜索；跨节点自动寻优、异构 GPU 和 elastic training 放入实验目录。

### 4.3 TensorLayout、通信原语和生命周期

#### 代码位置

- `src/aitrainer/layout.py`
- `src/aitrainer/parallel/collectives.py`
- `src/aitrainer/lifecycle.py`
- `src/aitrainer/overlap/`

#### 开发内容

实现 `TensorLayout`：

```python
@dataclass(frozen=True)
class TensorLayout:
    kind: Literal["replicated", "partial", "sequence", "head", "hidden"]
    shape: tuple[int, ...]
    dtype: torch.dtype
    group: object | None
    shard_dim: int | None = None
    valid_lengths: torch.Tensor | None = None
```

实现带自定义 autograd 的原语：

```python
copy_to_tp(x)          # forward identity, backward all-reduce
reduce_from_tp(x)      # forward all-reduce, backward identity
scatter_to_tp(x)       # forward split, backward all-gather
gather_from_tp(x)      # forward all-gather, backward split
scatter_to_sequence(x) # forward sequence split, backward all-gather
all_to_all_layout(x, scatter_dim, gather_dim, group)
```

实现 `AsyncOp`、`ExecutionScheduler` 和统一 `drain()`：

- 每个 op 记录 group、stream、peer、tensor、micro-batch 和提交时间；
- consumer stream 显式 wait producer event；
- tensor 最后使用后才 release/归还 buffer pool；
- optimizer、checkpoint、异常退出前 drain 所有 pending op；
- 任何 timeout 都打印完整上下文。

#### 验收标准

- replicated/partial/sequence/head/hidden 的 layout 转换可逆；
- CPU/Gloo 模拟 group 可测试 shape 和 autograd；
- CUDA/NCCL 测试无隐式 `barrier` 依赖；
- 故意延迟或失败的异步 op 能被超时诊断和 drain。

### 4.4 ModelAdapter、ModelSpec 和 PP stage 切分

#### 代码位置

- `src/aitrainer/adapters.py`
- `src/aitrainer/model_spec.py`
- `src/aitrainer/parallelizer.py`
- `src/aitrainer/plugins/transformer.py`

#### 开发内容

`ModelAdapter` 必须提供：模型构建、layer 列表、embedding/head、参数共享、输入输出规格、loss 输出适配和每层成本估算。

`StageSplitPolicy` 支持：

- `uniform_layers`：仅用于基线；
- `parameter_count`：按参数量均衡；
- `flops`：按预计 FLOPs 均衡；
- `memory_balanced`：同时考虑 activation 和通信 buffer。

embedding、lm head、norm、MoE/稀疏层支持独立权重。stage plan 必须输出：层范围、参数量、FLOPs、激活量、预计显存、首尾输入输出 layout。

高级入口自动识别常见 Transformer；专家入口允许用户完全控制 stage split 和 layout。自动生成结果必须可导出为 JSON，供人工审阅。

- 当前设计文档第 4、6 节：ModelAdapter、并行化顺序；

第一版只支持层级 Transformer；跨模块共享参数、非顺序网络、MoE 专家动态路由需由适配器显式声明，不能自动猜测。

### 4.5 Megatron 风格 TP

#### 代码位置

- `src/aitrainer/parallel/tp.py`
- `src/aitrainer/plugins/transformer.py`
- `src/aitrainer/checkpoint/`

#### 开发内容

实现两种基础模块：

**Column Parallel Linear**

- 沿输出维切分权重；输入默认 replicated；
- 输出默认保持 output-sharded；只有下游需要完整 hidden 时 all-gather；
- bias 保持对应分片，支持 `skip_bias_add`。

**Row Parallel Linear**

- 沿输入维切分权重；输入要求 hidden-sharded 或先 scatter；
- 输出为 partial，必要时 all-reduce；
- bias 只在约定位置添加一次。

QKV 和 MLP 的默认 plan：

```text
q_proj/k_proj/v_proj: Column Parallel
o_proj:               Row Parallel
gate_proj/up_proj:    Column Parallel
down_proj:            Row Parallel
```

实现维度整除检查、`input_is_parallel`、`gather_output`、`skip_bias_add`、参数 shard metadata、sharded state dict 和单卡 dense 对照。

异步 gradient all-reduce、gradient accumulation fusion、fused bias 仅作为独立开关；所有 handle 必须在梯度裁剪和 optimizer step 前 wait。

#### 参考内容

- `references/Megatron-LM/megatron/core/tensor_parallel/layers.py`：`ColumnParallelLinear`、`RowParallelLinear`、`linear_with_grad_accumulation_and_async_allreduce`；
- `references/Megatron-LM/megatron/core/tensor_parallel/mappings.py`：copy/reduce/scatter/gather/sequence scatter 的 autograd 原语；
- `references/Megatron-LM/megatron/core/tensor_parallel/utils.py`：tensor split 和整除检查；
- 当前设计文档第 9.2 节：TP 布局和通信语义。

#### 验收标准

- TP=1 与 dense linear 数值一致；
- TP>1 的前向、反向、梯度、checkpoint 恢复一致；
- 不必要的 gather/reduce 可被 layout checker 识别；
- QKV/MLP hidden/head 维度错误在启动前报错。

### 4.6 Ulysses 和 Megatron 式 SP

#### 代码位置

- `src/aitrainer/parallel/sp_ulysses.py`
- `src/aitrainer/parallel/sp_sequence.py`
- `src/aitrainer/parallel/collectives.py`

#### 开发内容

**Ulysses attention**：

```text
Q/K/V: [B, L/P, H, D]
all-to-all: scatter head(dim=2), gather sequence(dim=1)
attention: [B, L, H/P, D]
all-to-all: scatter sequence(dim=1), gather head(dim=2)
输出: [B, L/P, H, D]
```

实现：sp group、变长 `seq_lens`、padding/mask、RoPE 全局 offset、contiguous 检查、all-to-all autograd、只在 stage 边界 gather。

**Megatron Sequence Parallel**：

- LayerNorm/Dropout 输入按 sequence shard；
- Column/Row Parallel Linear 使用 sequence scatter、reduce-scatter、all-gather；
- 与 TP plan 组合时明确每个模块的 layout，防止重复切分。

#### 参考内容

- `references/uylesses/distributed/ulysses.py`：`distributed_attention` 的两次 all-to-all；
- `references/uylesses/distributed/util.py`：`all_to_all`、`all_gather`、`gather_forward`；
- `references/uylesses/distributed/sequence_parallel.py`：`sp_dit_forward` 的 sequence chunk、`rope_apply` 的全局位置切片、`sp_attn_forward`；
- `references/Megatron-LM/megatron/core/tensor_parallel/mappings.py`：`scatter_to_sequence_parallel_region`、`gather_from_sequence_parallel_region`、`reduce_scatter_to_sequence_parallel_region`。

#### 边界和验收

第一版 Ulysses 只支持 `L/H` 可整除、固定 batch shape 或显式 padding；动态不规则分片、context parallel 跨模型组合放入实验能力。必须测试变长 mask、RoPE 位置、attention 输出和梯度与单卡一致。

### 4.7 PP、P2P 和 1F1B

#### 代码位置

- `src/aitrainer/parallel/pp_shapes.py`
- `src/aitrainer/parallel/pp_p2p.py`
- `src/aitrainer/parallel/pp_schedule.py`
- `src/aitrainer/distributed_model.py`

#### 开发内容

实现 PP 通信协议：

```text
shape exchange → recv_forward → forward → send_forward
warmup → 1F1B steady state → cooldown backward
```

P2P communicator 至少提供：

```python
recv_forward(spec)
send_forward(tensor)
send_forward_recv_backward(tensor, spec)
send_backward_recv_forward(grad, spec)
recv_backward(spec)
drain()
```

每个 tensor 携带 stage、micro-batch id、forward/backward tag、shape、dtype。支持 GPipe 和非交错 1F1B；交错/virtual pipeline 先不进入 stable API。

1F1B 具体实现：warmup 保存 FIFO activation，steady state 交替前向/反向，cooldown 释放剩余 activation。最后 stage 计算 loss，其他 stage 传递 gradient；PP schedule 已完成反向时 Trainer 不得再次 backward。

#### 参考内容

- `references/Megatron-LM/megatron/core/pipeline_parallel/p2p_communication.py`：`P2PCommunicator` 的 recv/send 和组合 P2P；
- `references/Megatron-LM/megatron/core/pipeline_parallel/schedules.py`：`forward_backward_pipelining_without_interleaving`、`forward_backward_pipelining_with_interleaving`、warmup/steady/cooldown；
- `references/Megatron-LM/megatron/core/pipeline_parallel/combined_1f1b.py`：combined 1F1B 的 forward/backward 融合思路；
- `references/Megatron-LM/megatron/core/recompute.py`：pipeline activation recompute 策略；
- `references/DeepSpeed/deepspeed/runtime/pipe/p2p.py`：简化 P2P 生命周期参考。

#### 边界和验收

第一版不支持动态 tensor 数量、跨模块 pipeline 和 virtual stage；shape exchange、P2P timeout、2 stage GPipe/1F1B、activation 释放和梯度一致性必须通过分布式测试。

### 4.8 FSDP、MemoryPlanner 和 Activation Checkpoint

#### 代码位置

- `src/aitrainer/parallel/fsdp.py`
- `src/aitrainer/memory/planner.py`

### 4.13 分布式预训练模型初始化和加载

#### 4.13.1 结论和目标

可以避免“rank0 读取完整模型 → rank0 广播给其他 rank”的路径，但前提是 checkpoint 存储格式和加载器本身支持分片寻址。推荐路径是：

```text
所有 rank 读取小型 manifest
        ↓
每个 rank 根据 (pp, tp, dp) 坐标生成目标 shard plan
        ↓
每个 rank 直接从共享文件系统/对象存储读取自己需要的 CPU shard
        ↓
CPU pinned buffer → non_blocking H2D → 本 rank 参数/DTensor/FSDP shard
        ↓
只同步校验结果，不广播大参数
```

这会消除 rank0 的完整模型内存、CPU memcpy 和 GPU/NCCL broadcast 压力；但不会消除共享存储的总读带宽压力。所有 rank 同时读取同一文件时，还需要控制并发、利用 page cache 或先做按节点缓存。

#### 4.13.2 三种来源格式和处理策略

| 来源 | 推荐处理 | 是否需要 rank0 中转 |
| --- | --- | --- |
| 已分片 DCP/自有 sharded checkpoint | 每个 rank 按 ShardSpec 直接读取本地 shard | 否 |
| HF safetensors 多文件 checkpoint | 读取 index，按 byte range/键定位；每个 rank 只读目标切片 | 否 |
| 单体 `.pt`/单体 safetensors | 离线转换为分片格式；临时方案可多 rank 并行读取后切片 | 转换阶段可能需要，但训练启动不应依赖 rank0 |

单体文件如果只能由 rank0 打开和解析，就无法在不增加其他存储读取的情况下消除 rank0 瓶颈。框架必须提供 `convert_checkpoint`，在训练前将单体模型转换为带 manifest 的 shard layout；转换后正式训练只走 per-rank direct read。

#### 4.13.3 Checkpoint manifest 和 ShardSpec

manifest 是所有 rank 共享的只读小文件，至少包含：

```json
{
  "format_version": 1,
  "model_config_hash": "...",
  "tensor_schema_hash": "...",
  "world_size_at_save": 128,
  "logical_sharding": {"tp": 8, "pp": 4, "dp": 4},
  "tensors": {
    "layers.0.attn.q_proj.weight": {
      "global_shape": [4096, 4096],
      "dtype": "bfloat16",
      "layout": "column",
      "shards": [
        {"file": "rank_00000.safetensors", "offset": 0,
         "shape": [512, 4096], "offsets": [0, 0], "replica": 0}
      ]
    }
  }
}
```

`ShardSpec` 必须表达：全局参数名、全局 shape、dtype、参数布局、目标 `(pp_rank,tp_rank,dp_rank)`、源文件、byte offset/length 或 tensor key、local shape、global offset、是否 replicated、是否需要 transpose/reshape/fuse、checksum。

源 checkpoint 的分片和当前运行的分片可以不同。loader 需要执行一个明确的映射：

```text
source shard(s) ∩ target shard
    → 必要的 slice/concat/transpose/fuse
    → local CPU tensor
    → target parameter storage
```

不能假设“保存时 rank == 加载时 rank”。DP world size、TP size、PP size 变化时，必须依据全局坐标和 shard offsets 重新规划；如果格式或转换能力不支持，启动时拒绝恢复。

#### 4.13.4 每个 rank 的加载流程

```python
def load_model_distributed(model, checkpoint_uri, runtime, plan):
    manifest = reader.read_manifest(checkpoint_uri)       # 小元数据，可 all-rank 读取
    target = plan.build_target_shards(model, runtime.mapping)
    validate_schema(manifest, target)

    for shard in target.local_shards:
        # 只读取本 rank 所需的 source range/key，不构造完整 state_dict
        cpu_buf = reader.read_into_cpu(shard.source, pin_memory=True)
        cpu_buf = transform_to_target(cpu_buf, shard.transform)
        shard.target.copy_(cpu_buf, non_blocking=True)

    loader.drain_transfers()
    verify_local_checksums(model, target)
    all_ranks_agree_on_schema_and_checksums(runtime.group)
```

实施要求：

1. 模型先以 meta device 或空 storage 创建，禁止每个 rank 先构造完整 CPU 模型；
2. `ModelAdapter`/`ParallelPlan` 在 TP、PP、FSDP 包装前生成目标 shard plan；
3. 读取路径支持 CPU pinned buffer、按 tensor/byte range 读取、最大并发和 buffer quota；
4. CPU→GPU 使用专用 transfer stream 和 `non_blocking=True`，通过 event 与计算 stream 建立依赖；
5. 同一源文件被多个 rank 读取时，可以按节点建立 reader/cache，但禁止默认把完整文件复制到 rank0；
6. 共享权重（如 tied embedding/lm head）只保存一个 canonical tensor，其他参数通过 alias/link metadata 建立共享；
7. 读取完成后只做小型 metadata/checksum 集体校验，不对完整参数执行 broadcast；
8. 失败时记录 rank、tensor key、source file/range、目标 shard、已读字节和 transform；支持重试或干净退出。

#### 4.13.5 与 TP、PP、FSDP 的组合顺序

- **PP**：先根据 stage plan 确定本 rank 需要的层；非本 stage 参数不读取。embedding/head 按 adapter 的 canonical placement 处理。
- **TP**：直接读取 Column/Row Parallel 的目标切片；如果源是 dense 权重，按 `partition_dim` 计算 offset，不先读取完整矩阵。
- **FSDP/DP**：目标是 FSDP local shard。若源 checkpoint 只有 TP shard，loader 根据 DP shard offset 再切分；不要先 all-gather 成完整参数。
- **TP + FSDP**：目标 shard 是 TP 切片与 DP/FSDP 切片的交集；必须由 `ShardPlanner` 统一计算，不能由 TP 和 FSDP 各自切一次。
- **SP**：SP 通常不改变参数 shard，主要影响 activation layout，因此模型权重加载无需额外 SP broadcast。

推荐初始化顺序：

```text
Runtime/Topology
  → meta model
  → PP stage plan
  → TP/FSDP target shard plan
  → per-rank CPU direct read
  → pinned CPU → GPU/DTensor/FSDP storage
  → schema/checksum collective
  → optimizer/checkpoint/training loop
```

#### 4.13.6 DCP 和参考实现落点

优先支持 `torch.distributed.checkpoint` 兼容格式：每个 rank 构造包含本地目标 tensor 的 sharded state dict，调用 DCP reader 将数据直接填充到本地 CPU/GPU storage。DCP 的 metadata 可以由各 rank 读取/协调，但大 tensor 不应通过 rank0 state dict 中转。

- `references/Megatron-LM/megatron/core/dist_checkpointing/mapping.py`：`ShardedTensor`、global shape、offset、replica 和 shard metadata；

- `references/Megatron-LM/megatron/core/dist_checkpointing/strategies/fully_parallel.py`：fully parallel 的读写策略；
- `references/Megatron-LM/megatron/core/dist_checkpointing/strategies/cached_metadata_filesystem_reader.py`：共享 metadata 缓存和 filesystem reader；

#### 4.13.7 内存和吞吐控制

loader 需要独立配置：

```python
@dataclass(frozen=True)
class ModelLoadConfig:
    mode: Literal["direct_sharded", "rank0_legacy", "convert_then_load"] = "direct_sharded"
    reader: Literal["dcp", "safetensors", "torch"] = "dcp"
    cpu_buffer_bytes: int = 2 * 1024**3
    max_inflight_reads: int = 2
    pin_memory: bool = True
    verify_checksum: bool = True
    allow_world_size_change: bool = False
    node_cache: Literal["none", "page_cache", "local_nvme"] = "page_cache"
```

指标至少包括：每 rank 读取字节、读取吞吐、CPU→GPU 吞吐、最大 CPU/GPU loading memory、in-flight buffer 数、source file contention、metadata 时间和 checksum 时间。`rank0_legacy` 仅为兼容旧格式的显式 fallback，启动日志必须警告其内存和通信代价。

#### 4.13.8 验收标准和失败边界

- 2/4/8 rank 从同一 sharded checkpoint 直接加载，每个 rank 不持有完整模型；
- rank0 与其他 rank 的 peak CPU/GPU loading memory 同量级，不出现 rank0 特殊峰值；
- TP、PP、FSDP、TP+FSDP 的 local shard 与单卡 full model 数值一致；
- 加载 world size 与保存 world size 不同的已支持重分片场景；
- 单体 checkpoint 必须先转换，或明确走 `rank0_legacy`，不能静默使用广播；
- 缺失 shard、checksum 错误、schema mismatch、文件读取失败能定位并干净退出；
- 共享文件系统高并发读取有并发上限和退避，不因 loader 无界并发耗尽 CPU 内存。

### 批次 9：高级计算-通信重叠

#### 批次定位

批次 6、7 交付基础 `AsyncOp`、显式 wait/drain、FSDP 预取开关和 TP/PP/Offload 的异步通信入口；本批在这些能力之上实现 Megatron-LM 和 DeepSpeed 风格的细粒度调度、双缓冲、执行轨迹预取和在途资源反压。目标不是增加一个全局 `overlap=True` 开关，而是形成可以单独启停、验证和回退的五条流水：

```text
TP GEMM ↔ all-gather/reduce-scatter
backward gradient ready ↔ bucket reduce/reduce-scatter
optimizer/forward ↔ parameter all-gather
PP micro-batch compute ↔ activation/gradient P2P
GPU compute ↔ CPU H2D/D2H transfer
```

FSDP 继续独占 DP 参数分片、参数 all-gather、梯度 reduce-scatter 和 flat parameter 生命周期。本批不得读取或修改 FSDP 私有 flat-parameter 状态，不得在 FSDP 梯度上注册第二套归约 hook；框架只通过公开 API、module hook 和 `OverlapController` 协调 FSDP 外围的消费时机、资源预算、观测和最终 drain。

#### 开发位置和模块职责

将现有 `src/aitrainer/overlap.py` 原子迁移为 `src/aitrainer/overlap/` 包，公共符号由 `overlap/__init__.py` 重新导出，并在同一变更中更新仓库内调用方，不能同时保留文件和同名包或留下两套实现。

#### 开发项 9.1：统一异步运行时、双缓冲和资源反压

完善 `AsyncOp` 和 `OverlapController`：

- 状态至少包含 `created → submitted → ready → waited → released`，以及 `failed`、`timed_out`；非法状态转换立即抛出带 rank/group/op/buffer generation 的错误；
- 每个操作记录 producer stream/event、consumer stream/event、process group、tensor lease、micro-batch、bucket、提交时间和最晚等待点；
- 支持操作间依赖图，但热路径不得反复遍历全图；构建阶段冻结执行计划，step 内使用预编译的 predecessor/successor 索引；
- `wait()` 和 `drain()` 在一个 step 内幂等；异常时先保留原始异常，再按逆序 drain/release，清理失败作为附加上下文；
- 实现 DeepSpeed 风格 ping-pong buffer。通信读取 buffer 0 时，后续梯度写入 buffer 1；buffer 只有在 handle/event 完成且 generation 匹配后才能复用；
- 收集所有写入 bucket 的 producer stream，通信 stream 必须等待全部 producer；side stream 使用 tensor 后必须 `record_stream` 或记录等价 event；
- 实现 `max_inflight_ops`、`max_inflight_bytes`、`max_prefetched_param_bytes`、`max_transfer_bytes` 和每类操作独立配额；超过预算时等待最老的可回收操作，禁止无界提交；
- CPU/Gloo 和同步设备走同语义同步路径，不伪造 CUDA event；所有高级路径都有正式的同步 fallback。

配置必须按能力拆分，不能使用含义不完整的单一布尔值。例如：

```python
@dataclass(frozen=True)
class AdvancedOverlapConfig:
    enable_tp_bulk_overlap: bool = False
    enable_gradient_bucket_overlap: bool = False
    # enable_parameter_prefetch 已删除：它连启动期拒绝都不参与，
    # 唯一读它的是它自己的类型校验（见 test_every_config_field_is_read_somewhere）
    enable_optimizer_param_gather_overlap: bool = False
    enable_pp_p2p_overlap: bool = False
    enable_transfer_overlap: bool = False
    gradient_bucket_bytes: int = 25 * 1024 * 1024
    parameter_prefetch_bytes: int = 0
    max_inflight_ops: int = 2
    max_inflight_bytes: int = 0
    drain_timeout_s: float = 60.0
```

实际字段放入现有分层配置体系并遵守 `enable_` 命名规则；`0` 的含义必须在 schema 中明确为禁用或自动值，不能在不同字段中含义不一致。

#### 开发项 9.2：backward-ready gradient bucket

参考 Megatron-LM 的参数/梯度连续 buffer 和 DeepSpeed ZeRO-1/2/3 的 IPG bucket，实现非 FSDP reducer 或 distributed optimizer 所需的梯度流水：

1. 构建阶段按真实 backward ready 顺序和 dtype/group 生成 bucket；首个稳定 step 可记录顺序，后续顺序不一致时使对应 bucket 回退同步并重新建立 trace；
2. backward hook 只登记梯度 ready。只有 bucket 全部参数 ready、处于最后一个 gradient accumulation micro-batch 且 producer event 已满足时才提交；
3. 梯度写入连续 ping-pong buffer，超大单参数使用独立直接归约路径，不强制塞入普通 bucket；
4. distributed optimizer 使用 reduce-scatter，普通 replicated optimizer 使用 all-reduce；缩放、通信 dtype 和 accumulation dtype 的先后顺序必须与同步基线一致；
5. bucket 提交后允许后续层继续 backward；gradient clip、overflow 检查、optimizer step 和 checkpoint 前必须完成相关 bucket；
6. 限制在途 bucket/event 数，避免 allocator 和 NCCL backpressure；`finish_grad_sync()` 必须幂等并能在异常退出时统一 drain。

FSDP 模式只使用 FSDP 自带的 gradient reduce-scatter，本节 reducer 必须在启动校验阶段拒绝与 FSDP 同时接管同一参数。可以采集 FSDP 的公开 profiler 事件评估 bucket 粒度，但不能重复归约。

#### 开发项 9.3：Megatron 风格 TP bulk overlap

在 `ColumnParallelLinear`、`RowParallelLinear` 和 Sequence Parallel Linear 的 autograd 边界实现纯 PyTorch bulk overlap：

```text
异步 all-gather 输入 ─────────────┐
当前计算流执行 dgrad GEMM         │ overlap
wait all-gather → 执行 wgrad GEMM │
异步 reduce-scatter dgrad ────────┘ 与 wgrad GEMM overlap
```

实现要求：

- 将 forward AG、backward input AG、dgrad RS/AR 分别建模，不能用一个 TP overlap 开关隐式同时启用；
- autograd function 保存的 tensor、通信输出和临时 buffer 必须登记最后消费点；collective handle 不允许丢弃；
- 在使用 gather 结果前等待 AG，在上游消费 dgrad 前等待 RS/AR；wgrad 写入 optimizer/main-grad 前完成相应依赖；
- 对 QKV、attention output、FC1、FC2 分别采集 shape、GEMM 时间和通信时间，允许 capability/policy 基于算子类别关闭无收益的重叠；
- `tp=1`、CPU/Gloo、不支持异步 collective、动态 trace 失效时执行数值等价的同步路径；
- 不把 `CUDA_DEVICE_MAX_CONNECTIONS=1` 作为正确性条件。它只能由 benchmark 建议器作为可选环境调优提示，并记录在 artifact 中；
- 首个 stable 实现不依赖 Transformer Engine/APEX，不实现依赖专用 kernel 的 AG/RS-GEMM split/atomic overlap。未来若增加可选 kernel backend，必须通过现有 capability/fallback 接口接入，核心路径保持纯 PyTorch。

gradient accumulation fusion 只有在纯 PyTorch 的完整实现或已批准的可选 kernel backend 可用时才能暴露；不能以占位配置模拟 Megatron 的 APEX fused wgrad。

#### 开发项 9.4：参数 all-gather、执行轨迹预取和 optimizer overlap

实现 `ParameterPrefetchCoordinator`，吸收 Megatron-LM 的 bucket gather 链和 DeepSpeed ZeRO-3 的 trace-driven fetch/prefetch/release：

1. 构建/预热阶段记录 module、parameter、step、forward/backward/recompute 和最后使用位置；trace fingerprint 包含 module 顺序、共享参数、checkpoint/recompute 和配置；
2. 当前 module 进入前先提交缺失参数 fetch，只等待本 module 必需参数；当前参数可用后，在容量预算内预取后续 module；
3. 参数共享按最近使用和 reuse distance 决定保留/释放，不能因一个 module 完成就释放仍被其他 module 或 backward 使用的参数；
4. trace 不完整、控制流变化、graph break、参数集合变化或 fingerprint 不匹配时，立即停止旧预取计划并安全回退按需同步 fetch；稳定 trace 重新建立前不得恢复异步预取；
5. 当前 bucket wait 完成后可提交 next bucket，形成参数消费链；每个 bucket 防止重复 dispatch 和同一 receive buffer 并发写；
6. 支持在一个 optimizer group 更新完成后提交其参数 all-gather，用后续 optimizer group 的更新隐藏通信；forward 使用前仍由 pre-hook/消费点完成最终 wait；
7. FSDP 路径只通过公开预取能力和稳定 module 顺序进行协调，不自行写入 FSDP flat parameter。若锁定 PyTorch 版本无法提供安全接入点，`enable_optimizer_param_gather_overlap` 对 FSDP 明确标为 unsupported，不得访问私有属性绕过。

参数预取和 CPU parameter offload 共享同一驻留字节预算，不能各自计算配额后造成总显存超限。

#### 开发项 9.5：PP P2P overlap

由 `PipelineSchedule` 决定 P2P 的提交和等待时机，实现：

- 预提交下一 micro-batch 的 activation/gradient recv；
- `send_forward_recv_forward`、`send_forward_recv_backward`、`send_backward_recv_forward` 和双向组合操作；
- warmup、steady、cooldown 分别维护 recv/send handle 队列，不用全局 barrier 保证顺序；
- recv tensor 在计算消费前等待对应 recv handle；异步 send 的源 tensor 在 send 完成前不得释放、deallocate、覆盖或归还 buffer pool；
- 队列以 `(stage, virtual_stage, micro_batch, direction)` 为稳定 key，重复、缺失或乱序 handle 立即报错；
- schedule 在 capability matrix 中逐项声明是否支持 overlap。GPipe、非交错 1F1B 分别验证；未实现 virtual/interleaved schedule 时不暴露对应配置，也不以 Megatron 的 schedule 代码作为运行时依赖；
- flush/异常退出时 drain 全部 P2P handle，诊断输出 peer、方向、micro-batch、tensor spec 和最后进度。

延迟 embedding wgrad 和 virtual/interleaved 1F1B 不并入 stable PP 路径；若启动独立实验项，必须作为完整 schedule 实现和验证，不能在现有 schedule 中留下条件分支占位。

#### 开发项 9.6：Offload transfer 与计算统一流水

把批次 6 的参数/activation/optimizer offload 接入统一 transfer scheduler：

- 使用受配额控制的 pinned CPU buffer pool；H2D/D2H 通过 side stream 和 event 建立 producer/consumer 依赖；
- 参数路径形成“当前 module 计算、下一 module H2D、上一 module release”的流水；
- activation 路径保持 keep-last window，D2H 未完成前保留 GPU tensor lease，backward unpack 前只等待对应 H2D；
- optimizer offload 按 tile 实现“读取下一 tile、计算当前 tile、写回上一 tile”的三阶段流水时，必须一次性交付 buffer、错误、恢复和同步 fallback；没有完整 tile optimizer 时不暴露该开关；
- transfer、参数预取和通信共同受总 pinned-memory、GPU staging 和 in-flight byte 预算约束；
- NVMe/AIO 仍属于可选实验 backend，不进入核心依赖。没有该 backend 时配置校验明确拒绝，不保留空实现。

#### 开发项 9.7：跨 micro-batch overlap 实验项

参考 DeepSpeed Domino 设计独立的 `MicrobatchInterleaveScheduler` 实验项，将一个逻辑 batch 的两个 micro-batch 交错执行，用 micro-batch 1 的 attention/MLP 计算隐藏 micro-batch 0 的 TP all-reduce。该项与通用 Linear、普通 TP bulk overlap 和 PP schedule 解耦：

- scheduler 明确拥有两个 micro-batch 的 activation、RNG、通信 handle 和等待点；
- forward/backward、dropout RNG、gradient accumulation、checkpoint/recompute 和 loss normalization 必须同时实现；
- 启动时拒绝与未验证的 PP、动态 micro-batch、activation offload 组合；
- 记录额外激活显存和端到端延迟，只有吞吐收益覆盖显存/延迟成本时才建议启用；
- 该项初始状态为“未开始”，不阻塞批次 9 stable 出口；一旦进入开发，必须满足本文“实现完整性门槛”，不能只实现 forward 示例。

## 6. 开发状态记录表

### 6.1 状态定义和更新规则

开发状态只允许使用以下值：

| 状态 | 含义 | 是否可标记为开发完成 |
| --- | --- | --- |
| 未开始 | 尚未进入实现 | 否 |
| 开发中 | 已开始编码，但尚未满足全部验收项 | 否 |
| 待验证 | 功能代码已完成，测试证据尚不完整 | 否 |
| 验证中 | 正在执行单元、分布式、恢复或性能验证 | 否 |
| 已阻塞 | 存在明确的环境、上游 API 或设计阻塞 | 否 |
| 已完成 | 代码、验证、文档和审查全部通过 | 是 |

“实现完整”和“开发完成”是两个不同概念：

- **实现完整**：本开发项约定范围内的代码全部落地，正常/异常/cleanup/fallback 路径齐全，所有配置和入口已接线，没有临时代码或遗留项；此时可标记为“待验证”。
- **开发完成**：实现完整，并且本项要求的所有验证证据齐全；只有此时才可标记为“已完成”。

严格执行以下规则：

1. **禁止把“代码已编写”“PR 已合并”或“本地运行一次”视为开发完成。**
2. 只有该记录项的功能范围、批次出口条件、必需测试、恢复验证、文档和代码审查全部通过后，状态才能改为“已完成”。
3. 涉及分布式、异步通信、checkpoint、offload 或性能优化的条目，没有对应 GPU/NCCL、恢复或 benchmark 证据时最多标记为“待验证”。
4. 可选环境暂时不可用时标记为“已阻塞”或“待验证”，不得降低验收条件后标记完成。
5. 每次状态变更必须同时更新负责人、日期、证据链接/路径和备注；缺少证据的状态变更无效。
6. 若后续回归测试失败、依赖版本变化或 capability matrix 降级，已完成条目必须退回“验证中”或“已阻塞”。
7. 批次状态只有在该批所有“必须”条目均为已完成、批次出口条件通过后才可标记为已完成；实验项不阻塞批次，但必须保持单独状态。
8. 允许因当前缺少 GPU、节点或特定测试环境而暂缓验证；暂缓验证时状态只能是“待验证”或“已阻塞”，但在提交实现前仍必须完成可执行的测试代码、测试命令、预期结果和验证环境说明。
9. 任何进入“待验证”的开发项都不得含有实现遗留项；发现遗留项后必须退回“开发中”。

## 7. 统一验收清单

### 7.1 正确性

- 单卡 fp32/bf16 baseline；
- FSDP、TP、SP、PP、TP+FSDP、TP+SP 的前后向和梯度对照；
- GPipe/1F1B micro-batch 梯度累积等价性；
- 参数/optimizer/activation offload 开关等价性；
- compile/kernel/FP8 数值误差在配置阈值内；
- checkpoint 中断恢复和 RNG/sampler 连续。
- direct-sharded 模型加载与单卡 full model 数值一致；rank0 无完整模型峰值；

### 7.2 资源和并发

- 不同 rank mapping 的 topology 输出；
- stage FLOPs/参数/激活负载偏差；
- 峰值显存、buffer pool、CPU pinned memory quota；
- 异步 handle wait/drain、timeout、rank hang 和进程退出；
- 无未完成 collective、stream/event 或临时 checkpoint。
- 加载阶段无大参数 broadcast；每个 rank 的读取字节、CPU/GPU 峰值和 checksum 可审计。

### 7.3 性能

固定模型、数据、GPU、warm-up 和软件版本，至少记录：

```text

forward/backward/optimizer time
TP/FSDP/PP/offload communication time
communication wait time
pipeline bubble / GPU idle / overlap ratio
kernel launch / recompile / compile time
peak memory / allocation count / buffer pool hit rate
numerical error / fallback reason
```

结果保存为可比较的 benchmark artifact，任何“默认推荐”必须由重复测试证明收益。

## 9. 开发规范

### 9.1 分层依赖和模块边界

依赖方向必须保持单向：

```text
api/config/diagnostics
          ↓
trainer/distributed_model/parallelizer
          ↓
parallel/offload/kernels/overlap
          ↓
runtime/mesh/topology/lifecycle
          ↓
PyTorch/CUDA/NCCL
```

- 上层可以调用下层的稳定接口，下层不得反向 import `Trainer`、业务模型或应用数据逻辑；
- `parallel/` 只负责布局、通信和并行执行，不负责 optimizer、日志格式、数据集和业务 loss；
- `offload/` 只负责 storage 生命周期和 transfer，不重复实现 FSDP shard、TP layout 或 PP schedule；
- `kernels/` 只负责算子 backend 和 capability/fallback，不改变公共 `TensorLayout`；
- `overlap/` 只负责异步操作、依赖和 drain，不拥有模型参数或 optimizer；
- `runtime/mesh/topology` 不允许依赖具体模型类；
- 模型插件只能依赖 `api`、`adapters`、`layout` 和声明过的 backend 接口，不能直接访问私有 process group 全局变量；
- 参考实现目录不得加入生产包的 import path。

禁止通过循环 import、全局单例、隐式 monkey-patch 或模块级可变状态跨层传递上下文。确需共享的对象必须通过构造函数或明确的 context/provider 注入。

### 9.2 接口、数据结构和状态管理

- 公共接口使用 `Protocol`、抽象基类或不可变 dataclass 定义；
- 配置对象创建后不可原地修改，运行时派生状态放在独立的 `RuntimeState`；
- 过程结果优先使用结构化对象（如 `StepOutput`、`RankMapping`、`TensorLayout`、`AsyncOp`），避免返回位置含义不清的 tuple；
- 所有跨层对象必须明确 owner、生命周期、线程/stream 安全性和是否允许复用；
- process group、CUDA stream、event、buffer pool、临时目录等资源由创建它的组件释放；
- `start()/close()`、`prefetch()/release()`、`submit()/wait()/drain()` 等成对接口必须支持重复调用或明确抛出状态错误；
- 公共 API 不暴露 PyTorch 私有对象、内部属性或参考项目的全局状态；
- stable API 的行为变更必须更新版本说明和迁移文档，experimental API 允许快速变化但必须显式标记。

### 9.3 命名、类型和代码风格

- Python 遵循 PEP 8；统一使用项目 formatter、linter 和 import sorter，禁止通过忽略规则掩盖错误；
- 公共函数、方法、属性和 dataclass 字段必须有类型标注；张量参数补充 shape/layout/dtype 说明；
- 类名使用名词，动作使用动词；通信函数明确包含 `gather`、`scatter`、`reduce`、`all_to_all`、`send`、`recv` 等语义；
- `rank`、`local_rank`、`tp_rank`、`pp_rank`、`dp_rank` 不得混用；group 名称使用 `tp_group`、`sp_group`、`pp_group`、`dp_group`；
- 配置布尔值使用 `enable_`/`use_` 前缀，避免 `async`、`overlap` 等含义不完整的字段；
- 单个函数只负责一个阶段；通信提交、等待、数据变换和业务计算不得堆在同一函数中；
- 复杂调度使用小型私有函数分解 warmup、steady、cooldown、error cleanup 等路径；
- 注释解释“为什么”和通信/生命周期约束，不重复描述显而易见的代码；
- 禁止遗留 `pass`、`TODO`、调试 print、未使用 import、未使用配置字段和无测试的死代码进入 stable 分支。
- `NotImplementedError` 不能用于已纳入当前批次的路径；确属后续批次的能力不得注册到 stable factory/capability，也不得出现在默认调用链中。
- 禁止以 feature flag 隐藏未完成实现。feature flag 只用于选择两个已经完整实现并可明确校验的路径。

### 9.3.1 无遗留项规范

每个开发项必须在一个可审查的完整边界内交付。以下均视为实现遗留项：

- 公共方法存在但没有调用方，或配置项存在但运行时未消费；
- 只实现 happy path，没有输入校验、异常清理、timeout 或资源回收；
- 先使用 world group、rank0 broadcast、全局 barrier、完整 state dict 等临时路径，声称以后再按设计替换；
- 返回空 tensor、固定 loss、伪造成功状态或捕获异常后继续运行；
- 测试依赖 monkey-patch 绕过正式接口，生产调用链实际不可运行；
- 只在示例中实现核心逻辑，框架模块仍为空壳；
- 文档、capability matrix、checkpoint schema 或错误类型未同步更新；
- 性能路径缺少正式同步 fallback，或 fallback 与优化路径语义不同。

对于暂不开发的功能，应采取“整体不暴露”的方式：不创建公共配置、不注册 backend、不加入默认预设；如必须预留扩展点，只定义稳定 Protocol 和 unsupported capability，调用时在启动校验阶段明确拒绝。

### 9.4 配置与错误处理

- 配置校验集中在 `config.py/capability.py`，业务模块不重复实现同一规则；
- 组合校验必须在模型构建前完成，错误消息包含配置路径、实际值、要求和修复建议；
- 不支持的 PyTorch/CUDA/backend 组合使用专用异常（如 `UnsupportedCombinationError`），不能静默回退；
- NCCL timeout、OOM、shape/layout mismatch、dtype mismatch、未完成 async op、checkpoint schema 不一致分别使用可识别的错误类型；
- rank 相关错误必须记录 rank/group/peer/stage/micro-batch/module/tensor shape/dtype；
- rank 0 输出用户可读摘要，所有 rank 写入结构化诊断字段；
- cleanup 路径不能吞掉原始异常；清理失败追加到异常上下文；
- 只有用户明确启用的“安全降级”才能回退到 eager/同步/无 offload，并且必须记录 warning 和最终配置。

### 9.5 并行、异步和资源安全规范

- 任何 collective/P2P 必须显式传入 group，不得默认依赖全局 world group；
- 通信函数必须在入口校验 tensor device、dtype、shape、layout 和 group size；
- 异步 collective 返回 `AsyncOp`，提交方记录 producer，消费方显式 wait；禁止调用裸 `async_op=True` 后丢弃 handle；
- stream/event 必须通过 `lifecycle.py` 或 `OverlapController` 创建和登记，禁止各模块创建无记录的全局 CUDA stream；
- tensor 在 side stream 上使用前必须 `record_stream` 或通过 event 建立依赖；
- 参数、激活和通信 buffer 最后一次使用前不得释放，release 后不得继续读写；
- buffer pool 按 shape/dtype/layout 分桶，超过 quota 必须回退或抛出明确错误；
- 通信重叠优化必须有同步实现作为对照，默认先跑同步路径完成正确性验证；
- PP schedule、FSDP、Offload 只能各自声明自己拥有的 handle，统一由 `drain()` 负责收尾，避免重复 wait/free。

### 9.6 测试规范

每个功能至少配套以下测试层级：

1. **纯单元测试**：配置、layout、shape、rank mapping、状态机、错误类型，不依赖 GPU；
2. **CPU/Gloo 测试**：验证 collective 的 shape 和 autograd 语义；
3. **CUDA/NCCL 测试**：验证真实 stream/event、显存、P2P 和 dtype；
4. **分布式集成测试**：覆盖 2/4 GPU、不同并行组合和固定 seed 对照；
5. **恢复测试**：中断、checkpoint、RNG、sampler 和 optimizer 连续性；
6. **性能测试**：同步基线、优化版本、显存、wait time、吞吐和数值误差。

测试要求：

- 测试名称包含能力、并行尺寸和预期行为；
- 分布式测试设置超时，失败时输出 rank 状态和 pending op；
- 不使用不稳定的 wall-clock 断言作为唯一正确性依据；
- 性能测试固定 warm-up、重复次数、数据和软件版本；
- 每个 bug 修复必须新增回归测试；
- 不能因为 GPU 不可用而静默跳过必须运行的 GPU/NCCL 测试，CI 要明确标记环境缺失。
- 验证可以延后，但测试实现不能延后：功能 PR 必须包含完整的单元/分布式/恢复/性能测试入口、fixture、预期断言和目标环境说明；未实际执行的测试在状态表中标记为“未执行”，不得伪造通过。

### 9.7 性能代码规范

- 任何性能优化必须先提交同步/eager baseline，再提交优化实现；
- 代码中不得凭经验默认开启 prefetch、overlap、custom stream、fused kernel 或 FP8；
- 优化 PR 必须附 benchmark artifact：配置、拓扑、tokens/s、显存、通信 wait、数值误差和 fallback；
- kernel backend 必须有 eager fallback 和 capability probe；
- 不以减少 Python 行数为目标牺牲布局清晰度；
- 不在热路径中执行反复的字符串查找、模块遍历、隐式 device copy、同步 `item()` 或全局 barrier；
- profiler/NVTX 通过显式开关启用，不能污染默认性能；
- 只有重复基准证明收益且没有破坏稳定边界的优化，才能进入推荐预设。

### 9.8 文档、示例和提交规范

- 新增模块必须有模块 docstring，说明职责、输入输出、线程/stream 安全性和不负责的内容；
- 新增公共接口必须同步更新设计文档、开发规划、API 示例和 capability matrix；
- 每个并行 backend 至少提供一个 tiny model 示例和一个失败配置示例；
- PR 标题包含批次和能力，例如 `[Batch 3][SP] add Ulysses attention backend`；
- PR 描述必须列出代码位置、参考实现位置、许可证/版本差异、测试命令、benchmark 和默认行为变化；
- commit 保持单一目的，禁止把格式化、无关重构和功能改动混在同一提交；
- 合并前必须通过 formatter、linter、type check、unit test；涉及分布式能力还必须通过对应 GPU/恢复测试或明确记录环境阻塞。

### 9.9 代码审查清单

审查人至少检查：

- 是否违反依赖方向或引入循环 import；
- 是否存在隐式全局状态、未注入的 group/stream/device；
- layout 是否在模块边界明确，是否有不必要 gather/reduce/copy；
- async handle、stream、event、buffer 是否有 owner、wait 和 drain；
- 错误是否在启动阶段暴露，诊断是否包含 rank 上下文；
- stable/experimental 边界是否清楚，默认配置是否仍然安全；
- 单元、分布式、恢复和性能测试是否覆盖变更；
- 是否补充参考代码位置、许可证说明和用户文档。
- 是否存在 TODO/pass/NotImplementedError、占位实现、未接线配置、未消费返回值或仅实现 happy path；存在任一项不得批准进入“待验证”。

### 9.10 依赖和参考代码使用规范

项目以“最小依赖、优先使用 PyTorch 一等 API、参考实现不进入运行时”为原则。

#### 核心依赖白名单

核心包默认只允许依赖：

- Python 标准库；
- 项目锁定版本的 PyTorch、`torch.distributed`、`torch.distributed.checkpoint`、DeviceMesh/DTensor 等 PyTorch 一等 API；
- CUDA/NCCL 运行时及其 PyTorch 官方绑定。

配置解析、日志、校验、文件索引、线程/进程管理优先使用标准库实现。没有必要时不得引入新的配置框架、分布式框架、通信库或模型库。

#### 参考项目边界

- `references/uylesses`、`references/Megatron-LM`、`references/DeepSpeed` 只能用于阅读、对照、测试设计和算法提炼；
- 生产代码不得 `import references.*`，不得把参考仓库加入 `PYTHONPATH`；
- 不直接复制大段实现；若确需移植算法，必须重新适配项目的 `TensorLayout`、`AsyncOp`、错误和配置接口，并保留许可证审查记录；
- 参考项目中的私有 API、全局状态、CLI 配置体系和外部 kernel 不得隐式带入核心框架；
- 参考实现依赖的 Transformer Engine、FlashAttention、Triton、APEX、DeepSpeed CUDA extension、NVMe AIO 等都只能作为明确的可选 backend，不能成为基础安装依赖。

#### 可选依赖规则

- 可选依赖必须放在独立 extra/backend 中，并通过 capability probe 检查；
- 未安装可选依赖时，核心功能仍可使用 PyTorch/eager fallback；
- 用户没有显式启用时，不得 import、编译或初始化可选 backend；
- 每个可选依赖要记录版本范围、许可证、支持的 CUDA/PyTorch 组合、安装方式和回退行为；
- 可选依赖不能改变公共 API、TensorLayout 或 checkpoint schema。

#### 依赖变更流程

新增依赖前必须提交一份小型 ADR，说明：解决的问题、为什么标准库/PyTorch 无法满足、包体和启动成本、许可证、安全风险、替代方案、是否可选以及移除路径。代码审查必须检查锁文件、最小安装测试和无可选依赖的 fallback 测试。

## 10. 变更管理和代码审查要求

每个 PR 必须标注所属批次和稳定等级，并包含：

1. 变更的代码位置和对应设计章节；
2. 使用的参考实现路径及是否存在许可证/版本差异；
3. 新增配置和 capability matrix 变化；
4. 单元、分布式、恢复和性能测试结果；
5. 默认行为是否改变、回退路径是什么；
6. 对 layout/lifecycle/capability 契约是否有影响。
7. 对应开发项 ID，以及合并后应更新为“开发中”“待验证”还是“验证中”；未经完整验证不得在 PR 中直接改为“已完成”。
8. 实现完整性声明：列出正常/异常/cleanup/fallback 路径，并确认没有本批次遗留项；如果验证延后，列出未执行测试、所需环境和可重现命令。

如果新增或调整依赖，还必须附 ADR、许可证结论、最小安装验证、fallback 测试和移除方案。

涉及通信、offload、stream/event、checkpoint 或 optimizer 的改动必须由至少一名熟悉分布式运行时的开发者审查。未经测试的 experimental 能力不得进入 `aitrainer.api` 或默认预设。
