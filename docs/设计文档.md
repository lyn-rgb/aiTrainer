# 通用分布式训练基础框架：开发方案与路线图

> 本文将已有的设计设想整理为开发人员可以执行、测试和验收的方案。文中出现的代码是接口示意，不承诺在所有 PyTorch 版本中可以直接运行；具体 API 以项目锁定的 PyTorch 版本为准。

> 依赖原则：`references/uylesses`、`references/Megatron-LM`、`references/DeepSpeed` 仅作为机制和实现细节参考，不作为本项目运行时依赖。核心框架优先只使用 Python 标准库、项目锁定版本的 PyTorch/torch.distributed/DCP 及 CUDA/NCCL；FlashAttention、Transformer Engine、Triton、APEX、DeepSpeed extension 等只能作为显式可选 backend，并提供 eager/PyTorch fallback。

## 1. 项目定位

### 1.1 目标

构建一个与具体模型和训练策略解耦的 PyTorch 训练基础框架。框架负责分布式运行时、设备拓扑、模型并行化、训练步编排、检查点和可观测性；模型开发者通过适配器和并行计划描述模型结构，业务方通过配置注入数据、优化器和损失函数。

首期目标是支持以下可组合能力：

- 单卡/多卡正确训练；
- FSDP 数据并行（优先交付）；
- TP 张量并行；
- PP 流水线并行；
- 与 TP 配套的 SP（序列并行）；
- AMP、梯度累积、梯度裁剪和可选的 `torch.compile`；
- 基于 `torch.distributed.checkpoint` 的可恢复训练；
- 统一的日志、性能统计和错误诊断。

### 1.2 非目标

以下内容不属于框架首期职责：

- 自动理解任意模型并生成可靠的 TP/PP 切分方案；
- 替代用户的模型定义、数据预处理、损失函数或业务指标；
- 在未验证的 PyTorch 实验性 API 上承诺跨版本兼容；
- 通过框架自动调优所有并行尺寸和硬件拓扑。

### 1.3 设计原则

1. **正确性优先**：每增加一种并行策略，都必须先有单卡对照和多卡一致性测试，再开放性能优化。
2. **显式依赖**：模型结构、切分方式和损失计算通过接口注入，不在框架内部写死 Llama、GPT 等模型逻辑。
3. **能力分级**：配置只允许启用当前版本已验证的组合；不支持的组合在启动阶段报错，而不是运行中静默降级。
4. **可观测、可恢复**：每次训练记录完整配置、软件版本、并行拓扑和随机状态，检查点可从任意 rank 数量恢复（若该版本支持）。
5. **渐进交付**：先交付 `pp=1,tp=1` 的单卡/FSDP，再逐步引入 TP、PP、SP、compile 和重叠优化。

## 2. 范围和前置约束

### 2.1 推荐基线

- Python、PyTorch、CUDA、NCCL 版本在项目环境文件中锁定，并在 CI 中固定验证；
- 使用 `torchrun` 启动，框架不负责分配节点和 GPU；
- CUDA 后端使用 NCCL，CPU 测试可使用 Gloo；
- 首期只支持 CUDA，设备抽象保留扩展点；
- `world_size = pp_size × dp_size × tp_size`，三个尺寸必须为正整数并与实际 world size 一致；
- SP 不是独立的设备维度，通常是 TP 计划中的 `SequenceParallel`，配置项使用 `sp_enabled`，并要求 `tp_size > 1`。

### 2.2 明确的组合边界

| 组合 | 首期策略 |
| --- | --- |
| 单卡 | 必须支持，作为所有分布式模式的基准 |
| FSDP（独立或作为 DP 轴与 TP/PP 组合） | 使用显式 DP group；组合入口已接入 |
| TP（`dp=pp=1`） | 在 FSDP 基线稳定后支持 |
| TP + FSDP | 使用正交 TP/DP group，按 TP → FSDP 顺序包装 |
| PP + TP/FSDP | 使用 PP stage → TP/SP → FSDP 的组合入口，按具体 schedule 验证 |
| SP | 仅随已验证的 TP 模型计划启用 |
| `torch.compile` + PP 通信 | 默认不支持整条 pipeline 编译，可编译 stage 内 block |

## 3. 总体架构

```text
应用层：ModelAdapter / ParallelPlan / DataProvider / LossFn / OptimizerFactory
                              │
框架层：Trainer ─ DistributedModel ─ Parallelizer
                              │
运行时：Runtime ─ DeviceMeshManager ─ ProcessGroup/Rank 映射
                              │
基础设施：CheckpointManager / Metrics / Profiler / Config & Validation
```

### 3.1 模块职责

- **Runtime**：初始化和销毁 process group，设置当前设备，处理异常退出和 rank 信息。
- **DeviceMeshManager**：创建命名的 `(pp, dp, tp)` `DeviceMesh`，暴露子 mesh、全局/局部 rank 和拓扑元数据。
- **TopologyPlanner**：读取 GPU/NVLink/PCIe/InfiniBand 拓扑，生成 TP/PP/DP 的物理 rank mapping；TP 优先放在同一高速互联域内。
- **ModelAdapter**：构建原始模型（支持 meta 初始化）、声明层列表、embedding/head、输入输出规格，并按 stage 返回模型片段。
- **ParallelPlan**：描述 TP/SP 样式、FSDP wrap policy、PP 切分规则、参数共享和每层计算成本。计划由用户或模型插件提供。
- **MemoryPlanner**：估算参数、梯度、优化器状态、激活和通信缓冲的峰值，选择 checkpoint、recompute、offload 和 buffer 复用策略。
- **KernelBackend**：探测 FlashAttention、融合 MLP/RMSNorm、Transformer Engine、Triton/CUDA 等 kernel 能力，并提供 eager fallback。
- **OverlapController**：统一管理异步 collective、P2P、H2D/D2H、bucket、stream/event 依赖和最终 drain。
- **Parallelizer**：按确定的顺序将原始 stage 转换为 TP → FSDP（必要时 compile）的可执行模型，执行兼容性检查。
- **DistributedModel**：屏蔽普通模型和 pipeline schedule 的差异，对 Trainer 提供统一的 `train_step`、`parameters`、`no_sync`（若可用）和状态访问接口。
- **Trainer**：负责 epoch/step、AMP、梯度累积、反向、梯度裁剪、optimizer/scheduler、日志和评估触发；不负责猜测模型内部结构。
- **DataProvider**：提供数据集和 collate；框架负责按 DP 组设置 sampler/epoch，PP 的 micro-batch 由执行器处理。
- **CheckpointManager**：保存/加载模型、优化器、scheduler、step、配置、RNG 和数据迭代状态。
- **Metrics/Profiler**：只在约定 rank 汇总和写出指标，支持吞吐、显存、通信/计算时间及 profiler trace。

极限性能模式下，整体执行链为：

```text
硬件拓扑探测 → RankMapping → 并行候选/成本评估 → 布局计划
       → MemoryPlan/KernelBackend → TP/SP/PP/FSDP 包装
       → OverlapController 调度 → Profiler 验证和反馈
```

### 3.2 拓扑规划和成本模型

`TopologyPlanner` 读取节点、GPU、NUMA、NVLink/NVSwitch、PCIe 和跨节点网络信息，默认将 TP 放在同一高速互联域，PP 放在相邻 stage，DP/FSDP 填充其余设备。任何逻辑 mesh 都要保存实际 global rank 列表，禁止假设连续 rank 必然具有最快链路。

首期成本模型不负责一次性找到全局最优，但必须提供：

```python
estimate_memory(model_spec, parallel_plan, batch_spec)
estimate_communication(model_spec, parallel_plan, topology)
estimate_pipeline_bubble(stage_plan, num_microbatches)
validate_parallel_plan(plan, hardware_budget)
```

阶段 5 可基于这些估算生成多个候选，并运行短 warm-up benchmark 选择吞吐/显存约束下的方案。自动选择必须可关闭、可复现，并输出候选、评分和最终选择原因。

## 4. 稳定接口

接口应以 `Protocol` 或抽象基类定义，具体实现放在模型插件或应用代码中。

```python
class ModelAdapter(Protocol):
    def build(self, *, device: torch.device | str, dtype: torch.dtype | None) -> nn.Module: ...
    def layers(self, model: nn.Module) -> Sequence[nn.Module]: ...
    def estimate_layer_cost(self, layer: nn.Module, input_spec: object) -> object: ...
    def split_stage(self, model: nn.Module, *, policy: object) -> nn.Module: ...
    def input_spec(self) -> object: ...       # pipeline shape/dtype 说明
    def output_for_loss(self, output: object, batch: object) -> object: ...

class ParallelPlan(Protocol):
    def tp_plan(self, stage: nn.Module, *, tp_mesh: object) -> object: ...
    def fsdp_wrap_policy(self, stage: nn.Module) -> object | None: ...
    def validate(self, model: nn.Module, topology: object, config: object) -> None: ...

class DataProvider(Protocol):
    def train_dataloader(self, *, dp_group: object, seed: int) -> Iterable[object]: ...

class LossFn(Protocol):
    def __call__(self, model_output: object, batch: object) -> torch.Tensor: ...

class OptimizerFactory(Protocol):
    def build(self, parameters: Iterable[nn.Parameter]) -> torch.optim.Optimizer: ...

class ModelSpec(Protocol):
    """可选的高层模型描述；常见 Transformer 可由框架自动生成。"""
    def architecture(self) -> str: ...
    def parallel_defaults(self) -> object: ...
```

模型适配器必须明确参数共享（例如 tied embedding/lm head）和 pipeline 的首尾输入输出；框架不得通过字符串通配符猜测模块语义。常见模型可以作为独立插件提供默认 `ParallelPlan`，但不能成为核心模块的隐含依赖。

为兼顾易用性和可控性，提供两级入口：

- **高级入口**：对常见 Transformer 使用 `Trainer.from_model(model, config, dataset)`，自动生成 `ModelSpec`、默认 TP plan 和按计算成本的 stage 切分；
- **专业入口**：专家显式提供 `ModelAdapter`、`ParallelPlan`、`KernelBackend` 和 `TopologyPlanner`，完全控制布局、通信和切分。

高级入口生成的计划必须打印并可导出，用户可以在运行前审阅或转为专业入口继续修改。

公共 API 分层如下：

```text
aitrainer.api           # 配置、Trainer、ModelAdapter 等稳定接口
aitrainer.parallel      # 已通过集成测试的 TP/SP/PP/FSDP
aitrainer.backends      # 可替换的 kernel、通信和 offload backend
aitrainer.experimental  # FP8、NVMe、virtual pipeline、自定义 CUDA stream
```

实验能力必须显式开启并在日志中标记版本；不能通过修改 stable API 的默认行为获得实验性能。

DataProvider 还必须声明 DP sampler、epoch 更新、micro-batch 拆分、variable-length padding/mask、有效 token 数、loss normalization、streaming 恢复位置和 host prefetch/pinned memory 策略。这样 PP、SP 和梯度累积可以共享同一 batch contract。

## 5. 配置和启动校验

配置建议使用嵌套 dataclass 或等价的不可变配置对象，至少包含：

```python
@dataclass
class FrameworkConfig:
    pp_size: int = 1
    dp_size: int = 1
    tp_size: int = 1
    sp_enabled: bool = False
    sp_backend: Literal["none", "ulysses", "megatron"] = "none"
    pp_schedule: Literal["none", "gpipe", "1f1b"] = "none"
    precision: Literal["fp32", "bf16", "fp16"] = "bf16"
    grad_accumulation_steps: int = 1
    grad_clip_norm: float | None = None
    compile_enabled: bool = False
    compile_mode: str = "default"
    compile_dynamic: bool = False
    fsdp_sharding: str = "FULL_SHARD"
    fsdp_forward_prefetch: bool = False
    fsdp_limit_all_gathers: bool = True
    offload: "OffloadConfig | None" = None
    overlap: "OverlapConfig | None" = None
    checkpoint_interval: int = 0
    seed: int = 42
```

配置按领域拆分为 `ParallelConfig`、`PrecisionConfig`、`MemoryConfig`、`CommunicationConfig`、`CompileConfig` 和 `CheckpointConfig`；上面的扁平形式仅用于展示合并后的最终配置。框架应提供可复用预设：

```python
ConfigPreset.single_gpu()
ConfigPreset.fsdp()
ConfigPreset.tp()
ConfigPreset.tp_fsdp()
ConfigPreset.memory_saving()
ConfigPreset.performance()
```

预设不是隐藏默认值：启动时必须输出展开后的完整配置、实际 backend、rank mapping 和所有自动降级。

启动前必须检查：

- 并行尺寸乘积等于 `dist.get_world_size()`；
- `sp_enabled` 时 `tp_size > 1`，并行计划确实提供 SP 样式；
- PP 的 micro-batch 数量满足所选 schedule 的要求；
- `fp16` 才创建 `GradScaler`，`bf16` 默认不使用 scaler；
- `forward_prefetch` 仅在静态执行顺序且版本支持时开启；
- compile、DTensor、FSDP、PP 的组合在 capability matrix 中标记为已验证；
- 共享参数、空 stage、不整除层数、动态 shape 等情况有明确处理策略。
- precision 拆分为 parameter、compute、gradient、reduce、optimizer dtype，并校验其合法组合；
- topology mapping、kernel backend、offload 和 overlap 的 capability matrix 均已探测；
- 未完成 capability 验证时，`validate`/`dry-run` 必须在训练开始前失败。

提供不改变训练状态的诊断命令：

```text
aitrainer validate --config config.yaml
aitrainer inspect-topology
aitrainer dry-run --model tiny-transformer
```

输出至少包括版本、GPU 拓扑、各维度 process group、tensor layout、预计显存、micro-batch、backend、unsupported 组合和回退路径。

## 6. 模型并行化流程

每个 rank 执行相同的生命周期，只有 stage 内容和局部 rank 不同：

1. 初始化 process group，设置 `LOCAL_RANK` 对应的 CUDA 设备。
2. 根据配置创建 `DeviceMesh("cuda", (pp, dp, tp), ("pp", "dp", "tp"))`，记录 rank 映射。
3. 通过 `ModelAdapter` 在 meta 或指定设备上构建原始模型，并完成权重初始化/加载。
4. 调用 `split_stage`，先确定当前 PP stage 的模型边界；embedding 只放首 stage，head/norm 按适配器声明放置。
5. 在当前 stage 上调用 `parallelize_module(stage, tp_mesh, tp_plan)` 应用 TP/SP。TP 计划必须声明输入输出布局和必要的 gather/reduce。
6. 在 TP 后按 wrap policy 应用 FSDP，FSDP 的 process group/mesh 只覆盖 DP 维度；当前实现使用 `use_orig_params` 和显式 DP group，不把 TP/PP group 传入 FSDP。
7. 按配置编译 stage 内的 block 或 stage；不默认编译包含 PP P2P 通信的完整模型。
8. 创建 `DistributedModel`、optimizer、scheduler、dataloader 和 checkpoint manager。

推荐的默认顺序是 **拓扑/rank mapping → PP 切分 → TP/SP → FSDP → MemoryPlan/KernelBackend → compile**。如果某一 PyTorch 版本要求不同顺序，必须在适配层中固定并记录原因，不能让调用方自行组合包装顺序。

PP 切分不能只按层数均分。`StageSplitPolicy` 至少支持 `uniform_layers`、`parameter_count`、`flops` 和 `memory_balanced` 四种策略，并对 embedding、lm head、MoE/稀疏层设置独立权重。计划输出每个 stage 的层范围、预计 FLOPs、参数量、激活量和显存预算；若 stage 负载差异超过阈值，启动时告警或拒绝。

## 7. 训练执行契约

`DistributedModel` 对外提供统一的训练步协议，并明确反向归属：普通模式由 Trainer 调用 `forward_loss` 后执行反向；PP 模式由 `pipeline_step`（内部 schedule）完成 micro-batch 的前向/反向和激活传递。两种模式都返回结构化的 `StepOutput(loss, metrics, tokens, is_last_stage)`，避免对同一个 loss 重复调用 `backward`。

训练步的逻辑约定如下：

```python
optimizer.zero_grad(set_to_none=True)
for micro_step, micro_batch in enumerate(batch_iterator):
    sync = micro_step == grad_accumulation_steps - 1
    sync_context = nullcontext() if sync else model.no_sync_if_supported()
    with sync_context, autocast_context:
        if model.uses_pipeline:
            output = model.pipeline_step(micro_batch)  # schedule 内部已完成反向
        else:
            output = model.forward_loss(micro_batch)
            loss = output.loss / grad_accumulation_steps
            if scaler is not None:
                scaler.scale(loss).backward()
            else:
                loss.backward()

if scaler is not None:
    scaler.unscale_(optimizer)
clip_grad_norm_if_configured(model.parameters())
if scaler is not None:
    scaler.step(optimizer); scaler.update()
else:
    optimizer.step()
scheduler.step_if_configured()
```

实际实现必须区分普通模型和 pipeline schedule 两种反向路径，避免对已经由 schedule 完成反向的 loss 再次 `backward`。梯度累积时非最后一个 micro-step 使用 `no_sync`；PP schedule 的同步语义以其官方 API 为准。

PP 模式若启用 fp16，`pipeline_step` 必须通过 schedule 支持的 loss scaling/optimizer 接口接入 `GradScaler`；若该版本 API 不支持，则启动校验应拒绝该组合，而不是退回未缩放的 fp16 训练。

## 8. 并行策略实现要求

### 8.1 FSDP

- 首先支持 `FULL_SHARD`，后续再扩展其他策略；
- 明确 wrap policy（通常按 Transformer block），避免把整个 pipeline 当作一个不可调度的大模块；
- `use_orig_params`、mixed precision、prefetch 等选项必须受版本探针和测试覆盖；
- `limit_all_gathers` 默认以显存安全为先，性能调优时再基准测试；
- FSDP 参数状态、梯度裁剪和 state dict 只能通过框架封装的方法访问。

### 8.2 TP/SP

使用 `torch.distributed.tensor.parallel` 的标准 style（如 `ColwiseParallel`、`RowwiseParallel`、`SequenceParallel`）。计划必须说明：

- 哪些模块被切分；
- 输入/输出是 replicated、sharded 还是 partial；
- 残差、LayerNorm、embedding、输出头所需的 gather/reduce；
- hidden size、attention head 数等维度能否被 `tp_size` 整除。

不建议在核心框架中直接调用私有 `_functional_collectives`；只有在性能实验模块中才允许封装，并配套版本锁定和回退方案。

### 8.3 PP

优先使用 `torch.distributed.pipelining` 的 `PipelineStage` 和已验证的 `ScheduleGPipe`/`Schedule1F1B`。适配器提供每个 stage 的输入输出规格和切分边界，框架验证 stage 数、micro-batch 数和 shape。自定义 `send/recv` 仅作为后续扩展，必须独立实现、测试和开关控制。

### 8.4 AMP 与 compile

- `bf16`：使用 `torch.autocast`，通常不使用 `GradScaler`；
- `fp16`：使用 autocast + scaler，并在裁剪梯度前 `unscale_`；
- FSDP mixed precision 与 autocast 的职责和 dtype 要在配置中分别表达；
- compile 默认关闭。开启时先编译单个 block 或 stage，使用固定的 `mode/fullgraph/dynamic` 策略并记录首次编译耗时；动态 shape 和分布式通信导致 graph break 时应明确告警。

精度配置拆分为 `param_dtype`、`compute_dtype`、`grad_dtype`、`reduce_dtype` 和 `optimizer_dtype`。后续 FP8 backend 必须声明 scaling、overflow 检测和 FP32 保留算子（通常是 norm、softmax、loss）。每种精度模式都要定义数值误差预算、溢出恢复和 checkpoint dtype 规则。

### 8.5 Kernel Backend 和内存规划

Kernel backend 采用能力探测和 fallback：

- attention：FlashAttention/FlashAttention-2/3 或 eager attention；
- norm：fused RMSNorm/LayerNorm 或 PyTorch 实现；
- MLP：融合 bias、激活、残差的 kernel 或 eager 实现；
- optimizer：fused AdamW、CPU Adam 或普通 optimizer；
- dtype：BF16、FP16、FP8 按设备和版本探测。

不允许为了使用 fused kernel 改变公共 tensor layout；backend 必须声明输入布局、支持 dtype 和数值差异。`MemoryPlanner` 分析参数、梯度、优化器状态、activation、PP buffer、all-gather/bucket buffer 的生命周期，并在预算内选择 activation checkpoint、recompute、offload 和 buffer 复用。OOM 诊断必须指出当前 stage、module、micro-batch、buffer 类型和已占用预算。

### 8.6 优化器和梯度流水

框架应支持 distributed optimizer、optimizer state 分片、gradient bucket、gradient accumulation fusion、分片 gradient clipping，以及参数更新与通信重叠。每种 optimizer 需要在 capability matrix 中声明与 FSDP、TP、PP、CPU Offload 的兼容性；`optimizer.step` 前必须 drain 相关 gradient handle，不能依赖隐式同步。

## 9. 参考实现提炼和落地方案

本节将以下本地参考代码中的机制提炼为框架设计要求：

### 9.1 SP：Ulysses 风格序列并行

#### 9.1.1 数据布局和通信过程

Ulysses 风格的 attention 假定每个 rank 持有部分序列、完整或局部 attention heads：

```text
输入 Q/K/V：      [B, L / P, H, D]
第一次 all-to-all：按 H 切分，按 L 拼接
attention 输入：   [B, L, H / P, D]
局部 attention：   每个 rank 处理完整序列上的 H / P 个 head
第二次 all-to-all：按 L 切分，按 H 拼接
输出：             [B, L / P, H, D]
```

参考实现的关键操作是 `all_to_all(q, scatter_dim=2, gather_dim=1)` 以及反向的 `scatter_dim=1, gather_dim=2`。框架实现 `SequenceParallelBackend` 时应：

1. 从 `DeviceMesh` 获取独立的 `sp_group`/context-parallel group，不能默认使用全局 world group；
2. 在通信前显式 `chunk` 和 `contiguous`，优先使用 `all_to_all_single`，必要时保留 list 版本回退；
3. 在通信后立即验证 shape、dtype 和 layout，避免非连续 tensor 进入 fused attention；
4. 使用带 autograd 的通信封装，使反向自动执行逆向 all-to-all；
5. attention 结束后将结果还原为本 rank 的序列分片，只有在 head/unpatchify/loss 需要时才做 gather。

伪代码：

```python
def ulysses_attention(q, k, v, sp_group, seq_lens, attn):
    # q/k/v: [B, L_local, H, D]
    q = all_to_all(q, scatter_dim=2, gather_dim=1, group=sp_group)
    k = all_to_all(k, scatter_dim=2, gather_dim=1, group=sp_group)
    v = all_to_all(v, scatter_dim=2, gather_dim=1, group=sp_group)
    out = attn(q, k, v, key_lengths=seq_lens)
    return all_to_all(out, scatter_dim=1, gather_dim=2, group=sp_group)
```

#### 9.1.2 变长序列、位置编码和边界

- `L % sp_size == 0`、`H % sp_size == 0` 或可用 padding 的条件必须在启动时校验；
- 变长样本先按 batch 内最大长度 padding，同时传递每个样本的 `seq_lens`，attention mask 不能因 all-to-all 丢失；
- RoPE 等位置编码必须使用全局位置偏移。可在切分前生成全局频率后按 `sp_rank * local_length` 取片，或在每个 rank 根据全局 offset 生成；
- padding 和通信只对有效 token 计入 loss/吞吐；
- 输出 gather 是 stage 边界操作，不能在每个 block 后重复 gather。

#### 9.1.3 与 Megatron 式 SP 的区别

Ulysses 主要把 attention 的 head/sequence 维度重排，Megatron 的 Sequence Parallel 还会将 LayerNorm、Dropout 等激活沿序列切分，并在线性层边界使用 sequence scatter/gather 或 reduce-scatter/all-gather。框架应将两者建模为两个可组合但不同的能力：

- `UlyssesAttentionPlan`：只替换 attention 通信和布局；
- `MegatronSequencePlan`：为 LayerNorm、Dropout、Column/Row Parallel Linear 提供完整布局契约。

两者不能同时对同一 tensor 重复切分。计划必须声明每个模块的输入/输出布局（replicated、sequence-sharded、head-sharded、partial）。

### 9.2 TP：Megatron 风格列/行切分

#### 9.2.1 进程组和权重布局

参考实现通过 `parallel_state.initialize_model_parallel` 建立 TP、PP、DP 等正交 group。框架使用命名 `DeviceMesh` 表达相同关系，并为每个 group 暴露 rank、size、首尾 rank 和通信 backend；模型代码不得读取全局 rank 推断 TP rank。

Transformer 中的两个基础算子应抽象为：

| 算子 | 权重切分 | 输入要求 | 输出和通信 |
| --- | --- | --- | --- |
| Column Parallel Linear | 沿输出维切分 `W=[W_0,...,W_{P-1}]` | 输入通常 replicated | 输出为 `Y_i=XW_i`；仅下游需要完整 hidden 时 all-gather |
| Row Parallel Linear | 沿输入维切分，`X=[X_0,...,X_{P-1}]` | 输入 sequence/head/hidden 分片 | 各 rank 得到 partial output，随后 all-reduce；bias 只加一次 |

实现时需保留 `input_is_parallel`、`gather_output`、`skip_bias_add` 等显式选项，避免隐式通信。QKV 和 MLP 通常使用 Column → Row 配对，使中间激活保持分片。

#### 9.2.2 autograd 通信和初始化

Megatron 将 copy、reduce、scatter、gather 封装为带自定义 backward 的函数：forward 的 gather 对应 backward 的 split，forward 的 reduce 对应 backward 的 identity/copy。框架的 backend 至少要提供以下语义明确的原语：

```python
copy_to_tp(x)                 # forward identity, backward all-reduce
reduce_from_tp(x)             # forward all-reduce, backward identity
scatter_to_tp(x)              # forward split, backward all-gather
gather_from_tp(x)              # forward all-gather, backward split
scatter_to_sequence(x)        # forward sequence split, backward all-gather
reduce_scatter_sequence(x)    # forward reduce-scatter, backward all-gather
```

权重初始化直接生成本 rank 分片，禁止先在每个 rank 创建完整矩阵再切分。每个参数记录 `partition_dim`、`stride`、TP size 和原始 shape；保存检查点时写入 shard metadata，加载时按 metadata 重建，而不是依赖参数名称猜测。

#### 9.2.3 TP 校验和通信优化

- hidden size、FFN size、attention heads、KV heads 必须满足对应切分维度可整除；GQA/MQA 要单独校验 KV head 的映射；
- 禁止在不需要完整输出的层启用 `gather_output=True`；
- 可选开启 async all-reduce、gradient accumulation fusion 或 fused bias，但必须有 backend capability 和数值对照；
- 若使用异步梯度 reduce，必须在 optimizer step、梯度裁剪或参数复用前等待 handle；
- `CUDA_DEVICE_MAX_CONNECTIONS=1` 可作为特定硬件的基准变量，不设为框架默认值。

### 9.3 PP：Megatron 风格 1F1B 和 P2P

#### 9.3.1 Stage 和通信协议

PP rank 只持有本 stage 的层，stage 间通过专用 PP group 传递 activation 和 gradient。通信协议必须固定：tensor 数量、shape、dtype、micro-batch id、forward/backward tag；动态 shape 时先交换 shape metadata，再分配接收 buffer。

优先提供以下组合操作，减少通信往返并形成明确依赖：

```text
recv_forward()
send_forward()
send_forward_recv_backward()
send_backward_recv_forward()
recv_backward()
```

每个操作返回可等待的 work/event；后续计算只能消费已完成的 tensor。通信失败时输出 stage、micro-batch、peer 和 tensor metadata。

#### 9.3.2 1F1B 调度

非交错 1F1B 的一个 step 分为：

1. **warmup**：第 `pp_rank` 个 stage 先执行若干前向并保存输入/输出激活；
2. **steady state**：交替执行 forward 和 backward，同时执行 `send_forward_recv_backward`、`send_backward_recv_forward`；
3. **cooldown**：清空剩余 warmup 激活并完成反向。

`num_microbatches`、`pp_size`、stage rank 和 activation buffer 数量必须共同决定 warmup 数。交错 1F1B/virtual stage 作为后续能力，要求模型适配器返回可安全拆分的多个 chunk，并在检查点中保存 virtual stage 元数据。

#### 9.3.3 显存和反向

- 每个 micro-batch 的输入/输出 activation 进入 FIFO buffer；完成 backward 后立即释放引用；
- 可按 micro-batch 或 block 启用 activation checkpoint/recompute，避免同时保存整个 stage；
- 最后一 stage 计算 loss，其余 stage 只传递 activation/gradient；loss scaling 和 token normalization 必须跨 stage 一致；
- PP schedule 已完成 backward 时，Trainer 不得再次对返回 loss 调用 `backward`；
- 首期使用官方 `torch.distributed.pipelining` 或经过测试的本地 schedule，不能把 Megatron 的全局状态对象直接移植到核心框架。

### 9.4 CPU Offload：参数、优化器状态和激活分层实现

CPU Offload 必须分为三种模式，不能使用一个 `cpu_offload=True` 隐式开启全部行为：

| 模式 | 目标 | 首期建议 |
| --- | --- | --- |
| `optimizer` | Adam 一阶/二阶状态和 CPU optimizer | 阶段 4 支持 |
| `parameter` | FSDP/ZeRO 参数分片在 CPU 常驻，按 module fetch/release | 阶段 4 实验 |
| `activation` | checkpoint 输入或保存的激活异步 D2H，backward 前 H2D | 阶段 4 实验 |

#### 9.4.1 参数/优化器 offload

参考 DeepSpeed 的做法，参数 offload 采用“当前模块 fetch → 预取后续模块 → 当前模块使用 → release”的生命周期；优化器 offload 采用 CPU Adam 或等价的 CPU 实现。框架实现 `OffloadManager` 时必须：

- 以 pinned CPU memory 作为异步 D2H/H2D 的前提，提供 `pin_memory`、主机内存上限和 buffer pool 大小；
- 使用固定大小/按 shape-dtype 分桶的 buffer pool，避免每个 module 频繁分配释放；
- 用专用 transfer stream 发起 `copy_(..., non_blocking=True)`，用 CUDA event 和 `record_stream` 保证 GPU tensor 生命周期；
- 当前模块的参数必须在计算 stream 上可见后才能执行 GEMM；
- FSDP 已经管理参数 all-gather/release 时，offload 层只能接管明确的 storage 生命周期，不得再实现一套重复 shard；
- NVMe offload、异步 AIO 和 tile-based optimizer 暂不进入核心，后续作为独立 backend。

建议配置：

```python
@dataclass
class OffloadConfig:
    parameter_device: Literal["none", "cpu", "nvme"] = "none"
    optimizer_device: Literal["none", "cpu", "nvme"] = "none"
    activation_enabled: bool = False
    pin_memory: bool = True
    buffer_count: int = 4
    max_cpu_bytes: int | None = None
    prefetch_bucket_bytes: int = 0
    pipeline_read: bool = False
    pipeline_write: bool = False
```

#### 9.4.2 激活 offload

参考 DeepSpeed 的 activation offload engine，采用 pinned host buffer、side stream、有限 stash window 和 event：

1. forward 中只标记符合策略的 tensor（大于阈值、非 Parameter/Buffer、无 alias/stride-0 view）；
2. side stream 等待 compute stream 后执行异步 D2H，GPU tensor 使用 `record_stream`；
3. backward unpack 时让 compute stream 等待 D2H event，再恢复 tensor；
4. 使用 keep-last window 保留最早会马上用于 backward 的少量激活，避免异步拷贝尚未完成造成停顿；
5. 统计 offloaded/restored bytes、跳过原因和等待时间，超过 host memory quota 时回退到 checkpoint 或 GPU 保留。

首期可通过 `saved_tensors_hooks` 或显式 activation checkpoint wrapper 实现；不要对任意用户 tensor 全局 monkey-patch。CPU offload 与 compile、PP、重计算的组合需分别验证。

### 9.5 计算-通信重叠控制器

重叠不是单一开关，而是四类独立流水：

| 层级 | 可重叠通信 | 触发点 | 完成条件 |
| --- | --- | --- | --- |
| TP | all-reduce/all-gather/reduce-scatter | GEMM 或反向 dgrad 计算后立即提交 | 下一个依赖算子/optimizer 前 wait |
| FSDP | 参数 all-gather、梯度 reduce-scatter | 当前 block 计算期间预取下一 block | 当前 block 使用参数前 wait |
| PP | activation/gradient P2P | warmup/steady-state 中 send 与下一 micro-batch compute | 消费输入前 wait |
| Offload | D2H/H2D、NVMe AIO | transfer side stream | compute stream wait event |

实现 `OverlapController` 时遵循：

- 通信提交返回 handle，并关联 group、stream、tensor 和 micro-batch；
- 计算 stream 通过 `wait_stream`/`wait_event` 建立依赖，禁止依赖隐式全局同步；
- 对梯度使用 bucket/coalesced collective，bucket 满或反向 hook 触发时提交 reduce-scatter；
- FSDP 参数预取只在执行顺序稳定且已有 trace 时启用，设置 bucket/窗口上限，防止预取导致 OOM；
- PP 只在选定 schedule 支持组合 P2P 时开启 overlap；不支持的 schedule 启动时报错；
- 任何异步 handle 在参数复用、梯度裁剪、optimizer step、checkpoint 或退出前必须显式 drain；
- 默认使用高级 API 的内部 stream 管理，只有 profiler 证明收益后才暴露自定义 CUDA stream。

建议配置：

```python
@dataclass
class OverlapConfig:
    tp_comm: bool = False
    fsdp_prefetch: bool = False
    fsdp_prefetch_bucket_bytes: int = 0
    pp_p2p: bool = False
    offload_transfer: bool = False
    gradient_bucket_bytes: int = 25 * 1024 * 1024
    drain_timeout_s: float = 60.0
```

启动时生成 capability matrix，例如 `tp_comm × sequence_parallel × compile`、`pp_p2p × schedule`、`activation_offload × recompute`；未通过集成测试的组合必须标记为 unsupported。性能测试至少对比 eager/同步通信、异步通信、预取和 offload 四组，记录 overlap ratio、通信等待时间、tokens/s 和峰值显存。

### 9.6 推荐的实现抽象

```python
class SequenceParallelBackend(Protocol):
    def attention(self, q, k, v, *, group, seq_lens, layout): ...
    def gather_output(self, x, *, dim, group): ...

class TensorParallelBackend(Protocol):
    def column_linear(self, module, *, gather_output, input_layout): ...
    def row_linear(self, module, *, input_is_parallel, output_layout): ...

class PipelineSchedule(Protocol):
    def step(self, data_iterator, *, num_microbatches, forward_only=False) -> StepOutput: ...
    def drain(self) -> None: ...

class OffloadManager(Protocol):
    def prefetch(self, modules: Sequence[nn.Module]) -> None: ...
    def release(self, modules: Sequence[nn.Module]) -> None: ...
    def drain(self) -> None: ...

class AsyncOp(Protocol):
    def wait(self) -> None: ...
    def is_completed(self) -> bool: ...
    def bytes(self) -> int: ...

class ExecutionScheduler(Protocol):
    def submit(self, op: AsyncOp) -> AsyncOp: ...
    def wait_for(self, dependency: AsyncOp) -> None: ...
    def drain(self) -> None: ...
```

Parallelizer 通过依赖注入选择这些 backend，而不是在 `Trainer` 中写入 `all_to_all`、`send/recv` 或 CPU copy 细节。每个 backend 都要提供 eager/同步回退路径，便于定位通信错误。

所有参数、激活、梯度和通信 buffer 遵循统一的生命周期契约：创建后登记 owner 和 stream；使用前等待生产 handle；最后一次使用后释放或归还 buffer pool；optimizer、checkpoint、异常退出前调用统一 `drain()`。异步错误必须记录 rank、group、peer、stage、micro-batch、tensor shape/dtype 和 pending operation。

## 10. 检查点、恢复和可观测性

`CheckpointManager` 使用 `torch.distributed.checkpoint` 保存：

- 模型参数和 FSDP/DTensor 分片状态；
- optimizer、scheduler、scaler 状态；
- global step、epoch、数据 sampler 状态；
- 每个 rank 的 RNG（Python、NumPy、PyTorch、CUDA）；
- 完整的 FrameworkConfig、模型版本、代码版本和软件环境摘要。

保存采用临时目录加原子提交，写入 `manifest` 后才视为成功。加载时校验并行尺寸、参数 schema 和 dtype；若不支持跨 world size 恢复，应在启动时明确拒绝。

模型初始化和预训练权重加载不得默认采用“rank0 读取完整模型后广播”。对于已分片 checkpoint，所有 rank 应读取共享的 manifest，根据当前 `(pp, tp, dp)` 拓扑生成目标 shard plan，直接从文件系统/对象存储读取本 rank 所需的 CPU shard，再传输到本地参数、DTensor 或 FSDP storage。rank0 只参与小型 metadata/schema/checksum 协调，不中转大参数。单体 checkpoint 必须先转换为带 shard offset 的格式，或由用户显式选择 `rank0_legacy` 兼容路径；不得静默广播。

加载器需要控制 pinned CPU buffer、并发读取、节点缓存、CPU→GPU transfer stream 和 checksum；目标 shard 与源 shard 可以不同，TP/PP/FSDP 的切片交集由统一 `ShardPlanner` 计算。模型以 meta device 或空 storage 初始化，非当前 PP stage 的参数不读取。具体的 manifest、`ShardSpec`、DCP reader、单体 checkpoint 转换和验收要求见《开发方案与开发规划》4.13 节。

日志至少包含 rank 0 的 loss/学习率/吞吐，以及每个 rank 的 step time、显存峰值和通信异常。性能分析通过显式开关启用，不能默认拖慢训练。

运行时诊断必须覆盖 NCCL timeout、rank hang、OOM、异步 handle 未完成、checkpoint 半写入和进程异常退出。错误信息包含 rank/group/peer/stage/micro-batch/module/tensor metadata，并在安全范围内回收 process group、stream 和临时 checkpoint。OOM 可给出缩小 micro-batch、启用 checkpoint/offload 或调整并行尺寸的建议，但默认不自动改变训练语义。

- dry-run 不修改模型、optimizer、RNG 和 checkpoint 状态；

### 11.3 性能验收

在固定模型、数据、GPU 数和 warm-up 条件下记录 tokens/s、峰值显存、通信占比和编译耗时。任何“重叠优化”只有在基准测试有可重复收益时才设为推荐配置。

每个性能开关至少对比 eager/同步通信、异步通信、预取和 offload 四组，并记录：

- forward/backward/optimizer 分阶段耗时；
- TP/FSDP/PP/offload 的真实通信时间与 wait time；
- pipeline bubble、GPU idle ratio、overlap ratio；
- kernel launch 数、recompile 次数、首次 compile 时间；
- 显存峰值、分配次数、buffer pool 命中率；
- tokens/s、数值误差和失败回退路径。

性能结果必须保存为带完整配置、硬件拓扑和软件版本的 benchmark artifact，不能只记录单个吞吐数字。

## 12. 分阶段开发计划

### 阶段 0：工程骨架和单卡基线

交付配置、Runtime、ModelAdapter、Trainer、日志和最小 checkpoint；完成单卡 Transformer 的端到端训练与恢复。

**出口条件**：单元测试通过，固定 seed 的 loss 曲线可复现，代码布局和 API 冻结首版。

阶段 0 同时冻结三套基础契约：

- **布局契约**：每个模块输入/输出的 replicated、sequence-sharded、head-sharded、partial 状态；
- **生命周期契约**：参数、激活、梯度、通信 handle 的创建、等待、复用、释放和 drain；
- **能力契约**：PyTorch/CUDA/backend/并行组合的 stable、experimental、unsupported 状态。

### 阶段 1：FSDP 数据并行

实现 DeviceMesh 的 DP 子 mesh、按 block 的 FSDP wrap、AMP、梯度累积和分片 checkpoint。

**出口条件**：2/4 卡与单卡数值对照通过，OOM/异常退出有清晰错误信息。

### 阶段 2：TP（含可选 SP）

实现 ParallelPlan、Column/Row Parallel Linear、layout 校验和模型插件示例；先交付 Megatron 式 TP，再交付 Ulysses attention backend 和可选 Sequence Parallel；完成 TP 单独运行，再验证 TP+FSDP。

**出口条件**：hidden/head 维度校验、前后向闭环、性能基线和版本兼容矩阵齐全。

### 阶段 3：PP

接入官方 pipelining schedule 或等价的 stage adapter；实现 shape exchange、P2P work handle、GPipe 和非交错 1F1B 的 warmup/steady/cooldown，补充 activation buffer 回收和 PP checkpoint。

**出口条件**：2 stage 的 GPipe/1F1B 训练闭环，气泡和激活显存有可观测数据。

### 阶段 4：compile 与重叠优化

在已稳定组合上逐项加入 block/stage compile、FSDP prefetch、TP/PP 异步 collective、梯度 bucket、CPU optimizer/activation offload 和 profiler 驱动的优化。参数 offload、NVMe offload 和自定义 CUDA stream 先作为实验 backend，不改变默认路径。

**出口条件**：每个开关都有独立基准、回退路径和文档，不影响默认正确性。

### 阶段 5：性能专项和易用性完善

实现 topology-aware rank mapping、成本模型、自动 stage split、MemoryPlanner、KernelBackend、distributed optimizer、FP8、virtual pipeline、CUDA Graph 和更完整的 profiler；同时提供配置预设、高级模型入口、模型插件、`validate/inspect-topology/dry-run` 命令和统一错误诊断。

**出口条件**：高级入口可以在无需编写并行代码的情况下运行常见 Transformer；专业入口仍可替换所有 backend；性能模式在固定 benchmark 上可重现，实验能力不会污染 stable API。

### 开发优先级

| 优先级 | 必须完成的能力 |
| --- | --- |
| P0（正式实现前） | 布局/生命周期/能力契约、拓扑 rank mapping、配置分层与预设、capability matrix、PP 负载均衡、精度拆分、异步 handle/drain、高级 API、validate/dry-run |
| P1（基础版稳定后） | KernelBackend、MemoryPlanner、activation checkpoint、CPU optimizer/activation offload、通信 bucket/prefetch、性能 profiler、常见模型插件、完整 DataProvider contract |
| P2（性能专项） | FP8、virtual/interleaved pipeline、自动并行搜索、NVMe offload、CUDA Graph、自定义通信 stream、跨节点自动布局、elastic/异构训练 |

## 14. 主要风险和决策记录

- PyTorch 的 DeviceMesh、DTensor、TP 和 pipelining API 仍在演进，必须锁版本、写 capability probe，并把实验性 API 隔离在 `parallel/experimental`。
- TP+FSDP 的包装顺序和 state dict 语义存在版本差异；未通过集成测试前不得作为默认组合。
- 动态序列长度、参数共享和非 Transformer 结构会影响自动切分；这些情况交给 ModelAdapter 显式声明。
- 预取和异步通信可能增加显存；默认配置以稳定和显存安全为先，性能配置必须通过基准测试启用。
- Ulysses、Megatron-LM、DeepSpeed 的实现和许可证不同，参考代码只能作为设计依据；实际移植必须保留 NOTICE、许可证审查记录和版本锁定信息。
- 跨节点拓扑不是逻辑 mesh 能完全表达的；后续可增加 topology-aware rank 映射，但不在首期承诺自动寻优。

任何新增并行后端、模型插件或优化开关，都必须补充：接口说明、配置校验、最小示例、单元/分布式测试、checkpoint 兼容性说明和性能基线。这样才能保持框架真正“模型无关、策略可插拔、行为可验证”。
