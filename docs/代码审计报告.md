# aiTrainer 代码审计报告：实现缺陷与可用性缺口

> 审计对象：`aiTrainer`（`src/aitrainer`，约 6,360 LOC / 66 文件）
> 审计方式：静态阅读 + **真实 torch 实跑验证**（多智能体分块审计，关键结论由审计者逐条复核）
> 结论一句话：**工程纪律真诚，但核心分布式能力从未被执行过一次。仓库自己的测试套件在装上 torch 后立刻红 10 个，TP 与 SP 在任何 world size 下都抛异常。**

## FSDP2 迁移（2026-09-16，Stage A 已完成）

诉求是**一套代码里不要混着两代 FSDP 语义**。Stage A 把 `parallel/fsdp.py` 整体换成
FSDP2（`torch.distributed.fsdp.fully_shard`），并删掉 FSDP1 没有对应物的东西。

**删除**：`FSDPWrapper`、`fsdp_available()`（零调用方）、`full_state_dict_context()`、
`FSDPConfig` 的 `sharding`/`limit_all_gathers`/`forward_prefetch`/`execution_trace_complete`/
`cpu_offload`（5 个字段，全部到不了任何地方——设成 true 也既不切分也不预取）。

**替换**：

| FSDP1 | FSDP2 | 写错的后果 |
|---|---|---|
| `module.no_sync()` | `set_requires_gradient_sync(False)` | 每个 microbatch 一次完整归约：更慢、归约时机不同，**不报错** |
| `module.clip_grad_norm_` | `parallel.fsdp.clip_grad_norm_`（自己归约） | FSDP2 无此方法；`torch.distributed.fsdp.clip_grad_norm_` 在 2.9 **不存在**。看似等价的 `nn.utils.clip_grad_norm_` 会**静默给出分片范数**，见下 |
| `full_state_dict_context()` | `get_model_state_dict(..., StateDictOptions(full_state_dict=True))` | 默认返回的是 `DTensor`，`full_tensor()` 才拿到全局张量 |
| `FullyShardedDataParallel(m)` | `fully_shard(m)`（就地，返回同一对象） | 实例的类被换成 `FSDPLinear`：`type(x).__name__` 变了但 `x is module` 仍为真 |

**本轮实测出来的、文档里没有的语义**（`tests/multirank/worker.py`
的 `fsdp_accumulation_window_suppresses_reduction`）：累积窗口内 FSDP2 **完全不物化
`.grad`**（一直是 `None`，缓存在内部），下一个**同步**的 backward 才把全部累积一次性
归约——实测正好是 `4 * unit` 而不是 `1 * unit`。两个推论：

1. 窗口中途做 optimizer step 是**静默无效**的（`.grad` 是 `None`）。`fit` 的「只在该
   边界步进」不变式因此不只是性能问题，是正确性问题。
2. 原来那条多卡回归 `trainer_fit_fsdp_accumulation` **抓不到** `no_sync` 失效：两个
   rank 喂的是同一份数据，于是「每个 microbatch 各归约一次」和「边界归约一次」的和
   完全相同。新 case 因此使用**两个 rank 不同的数据**，并显式断言「归约值 ≠ 本 rank
   局部值」，否则整条测试是空转的。

**反向对照**：把 `no_gradient_sync` 还原成静默 no-op，新测试立刻变红
（`materialised_inside_window` 从 `[False, False, False]` 变成 `[True, True, True]`）。

**本轮靠「验证自己写下的注释」抓到的缺陷（`fsdp_grad_norm_is_global`）**：我先把
「`nn.utils.clip_grad_norm_` 在 DTensor 上算的是全局范数」写进了注释和文档，然后去
实测这句话——**它是错的**。DTensor 确实注册了 `linalg.vector_norm`（返回
`_NormPartial`，`full_tensor()` 是跨 mesh 求和），但 `nn.utils` 用 `torch.stack`
把各参数的结果堆成一个整体再取范数，而这个 stack 不认 DTensor，**静默退化成各分片
自己的值**。实测 dp=2、三层的模型：全局范数 0.678，rank 0 报 0.551、rank 1 报
0.395。两个后果都不报错：每个 rank 按**不同**系数裁剪，以及该裁的时候不裁。

修正为 `parallel.fsdp.clip_grad_norm_` 自己归约（与 `torch.nn.utils` 在普通张量上
逐位一致，已对 `norm_type=2`、`inf`、以及裁/不裁三种情形比对），并加了一条守卫：
输入是 DTensor 而范数返回值不是 DTensor 时**抛错**，把这个静默退化变成显式失败。
反向对照：换回 `nn.utils`，测试立刻以实测数字变红
（`0.5510668158531189 != 0.6779764294624329`）。

顺带删掉 `PipelineStage.clip_grad_norm_`：**零调用方**，且它的 fallback 正是上面
那条错路径——留着只会成为第二条会漂移的实现（审计报告 §9.3.1 对「公共方法存在但
没有调用方」的定义）。

**顺带修正的两处**：`wrap_fsdp` 不再把「无 mesh 的单进程」交给 FSDP2 自己推断
（那会走 env:// rendezvous，`world_size==1` 时报 `environment variable RANK expected`，
既没提 FSDP 也没提进程组）；`examples/fsdp_train`、`scripts/parallel_matrix.py` 两处
`full_state_dict_context` 调用点改用 `get_model_state_dict`。

**验收**：206 passed（+3 条新多卡 case）；`aitrainer.__all__` 142 → 143
（减 `FSDPWrapper`/`fsdp_available`，加 `clip_grad_norm_`/`no_gradient_sync`/`supports_gradient_sync`）；
`ruff` 91（未新增，逐文件与 `HEAD` 对比过）；
3 契约 kept；`parallel_matrix --config fsdp` 2 rank `parameter_max_abs_error = 0.0`；
`examples/fsdp_train` 2 rank 跑通。

**尚未开始**（见 `~/.claude/plans` 的迁移方案）：Stage B（自研 TP/SP → DTensor）、
Stage C（统一分片保存）。**Stage D（PP → `torch.distributed.pipelining`）被阻塞**：
原生 PP 在本机 2 rank 下触发 gloo 传输层硬崩溃
（`gloo::EnforceNotMet: op.nread == op.preamble.nbytes`，`pair.cc:253`），
尚未定位根因；现有自研 PP 在 2 rank 下与单进程逐位相同，因此保持不动。

## DTensor 迁移（2026-09-16，Stage B 已完成）

Stage A 之后，`parallel/tp.py` 与 `parallel/sp_sequence.py` 整体换成 torch 的
DTensor 原语。**动机不是风格，是 Stage C 的前提**：旧的自研 TP 把权重换成
「分片形状的普通 `Parameter`」，没有任何地方记录它是更大逻辑张量的一片，所以
`get_model_state_dict` 返回局部张量、DCP 把同名 key 当同一个逻辑张量、最后写入者胜出。
只有参数变成 `DTensor` 才能修好。

**删除**：`ColumnParallelLinear`、`RowParallelLinear`、`SequenceParallelLayerNorm`、
`gather_sequence`/`scatter_sequence`、`sequence_parallel_dropout`、
`parallel/collectives.py` 里 7 个自研 autograd 集合通信
（`copy_to_tp`/`scatter_to_tp`/`gather_from_tp`/`reduce_from_tp`/`*_sequence`/
`all_reduce_gradient`）、`PipelineStage.clip_grad_norm_`。`all_to_all_layout` 是
Ulysses 唯一还需要的东西，移进 `sp_ulysses.py`，`collectives.py` 随之删除。

**替换**：`parallelize_module` + `ColwiseParallel`/`RowwiseParallel`；
`plugins/transformer.py` 的 `TransformerTPPlan.styles()` 产出 torch style 对象。

**本轮实测出来的四件事**（每一条都不报错，或报错报得牛头不对马嘴）：

1. **空 plan 不是 no-op。** `parallelize_module(m, mesh, {})` 成功返回、什么都不切。
   实测 `tp_size=2` 配普通 `nn.Sequential`：参数数不变、无任何提示，每个 rank 拿完整
   副本各训各的。现在 `tp_size>1` 且 plan 为空**直接报错**。
2. **torch 的 `SequenceParallel` 不能这么用。** 它假定输入**已经是本 rank 的序列切片**，
   只做标注（`from_local(..., run_check=False)`）。喂它复制张量不会切分，只会把全局
   序列长度标成 `world_size` 倍——实测 (2,4,8) 的输入返回全局 (2,8,8) 的 DTensor，
   一路无事，直到下一个模块的 `view` 抛出
   `Sharding propagation failed ... args_schema=Spec(S(1) on (2, 8, 8))`，
   既没提 SP 也没提真正的原因。它只在「embedding 就吐序列分片、整条残差流分片」的模型上
   成立，那是模型的性质，框架无法给任意 `nn.Module` 装上。改成自研 style：
   输入侧 `Replicate → Shard`、输出侧 gather 回来。
3. **手写 `chunk` 取本地切片是静默错的。** 第一版 style 就是这么写的：chunk 的反向
   只给每个 rank 自己那一片的贡献，于是*复制*输入的梯度每 rank 只填了一半——实测
   输入梯度误差 `4.8e-03` / `7.0e-03`，正确值是 `9.3e-10`。写成布局迁移后 DTensor 的
   autograd 自动给出对应的 all-gather（即旧代码里 `gather_sequence` 手工做的那件事）。
4. **TP 参数变成 DTensor 之后，FSDP 就装不上了。** `fully_shard` 要求 DP mesh 与 TP
   mesh 共享父 mesh，而 `wrap_fsdp` 一直用 `DeviceMesh.from_group(dp_group)` 造独立 mesh：
   `tp_size=2 + fsdp.enabled` 在构造期直接失败（`FSDP requires the DP and model parallel
   TP/EP mesh to have the same parent mesh`），`dp_size=2` 单独跑却没事。修法是优先取
   `mesh.submesh("dp")`（同一父 mesh 的子 mesh）。**这个问题在 Stage B 之前不可能出现**
   ——那时没有 TP 的 DTensor 参数需要 FSDP 去对账。

**顺带修掉一个从未被执行过的脚本缺陷**：`scripts/parallel_matrix.py` 的 PP 分支
调用 `result.get("loss")`，而 `ScheduleOutput` 是 dataclass 不是 dict——该脚本的 PP 条目
在 world=4 下**一个 step 都没跑完过**。删除 SP 后首轮 4 rank 运行才暴露。

**反向对照（4 条，全部确认变红）**：
- 去掉空 plan 守卫 → 「静默复制」测试红（`assert False is True`）
- `prepare_input` 换回手写 chunk → SP 输入梯度红（`0.005377 < 1e-06` 失败）
- `prepare_input` 改成完全不切分 → **数值断言全过**，只有「norm 里的激活必须是
  `Shard(1)` 且本地序列长度为全局的 1/world」这条结构性断言红
  （`assert 'Shard' in '(Replicate(),)'`）。这条证明了结构断言不可省：一个什么都不切的
  style 会与 dense 参考逐位一致。
- DP mesh 换回独立 mesh → `dp=2,tp=2` 与 `tp=2+sp` 两条组合红（父 mesh 断言）

**验收**：213 passed（+4 条组合参数化：`dp=2` / `tp=2` / `tp=2+sp` / world4 的 `dp=2,tp=2`）；
`aitrainer.__all__` 143 → 136；`ruff` 90（比基线 91 少 1，删掉的两个模块带走了既有条目）；
3 契约 kept；7/7 示例；`parallel_matrix` 4 rank 四个组合条目全部 `passed`（此前 PP 两条从未跑通）。

**明确未做**：完整 Megatron 式 SP（整条残差流序列分片）需要模型配合，框架无法通用安装，
因此**只做 norm 自身的激活分片**，与旧实现语义相同；这一限制写在 `TransformerTPPlan.styles`
的 docstring 里。`sp_backend` 的 `ulysses` 与 `megatron` 在生产路径上**行为相同**——这是
「声明了但未接线」，已记入 `架构.md`。

## 分片保存统一（2026-09-16，Stage C 已完成）

Stage B 把 TP 参数变成 `DTensor` 之后，这一阶段才可能：删掉
`_reject_unsupported_sharding`，让 `save_sharded`/`load_sharded` 覆盖全部轴，
并拿到此前完全缺失的**重分片**能力。

**模板句式的结果**：tp=2 存的 checkpoint，在一个**没有进程组**的单进程里读进
dense 模型，`max|diff| = 0.000e+00`，形状是全局 `(8, 8)`。这同时换了 world size
和 TP 布局。旧文档记的是「换 world size 只能拒绝，不能转换」。

**PP 没有被 TP 的修复带上，而且它坏得更隐蔽。** Stage B 之后我实测了
pp=2 的往返：`max|diff| = 6.4e-01`，两个 rank 拿到的是**同一个**张量、且都
不是自己的——而 save 和 load 都报成功。根因不是 DTensor 能解决的：
`split_sequential` 给每个 stage 各自的 `nn.Sequential`，于是每个 stage 都从
`"0"` 开始命名，stage 0 的 `0.weight` 和 stage 1 的 `0.weight` 是不同张量同一个 key。
**只**把 key 按 stage 加前缀，往返立刻变成 `0.000e+00`——反证见下。

**修复**：`checkpointing._stage_prefix`。前缀只在 `pp_size>1` 时加，这是 key
唯一性的要求而非配置开关（单 stage 时 `0.weight` 本就唯一，布局不变）。

**反向对照**：把 `_stage_prefix` 改成恒返回空串 →
`test_sharded_checkpoint_round_trips_every_axis[pp]` 红（「the pp round trip changed
the weights」），而 `[tp]` 与重分片那条**仍然绿**。这条对照同时证明了两件事：
TP 是 Stage B 修好的（与前缀无关），PP 才是前缀在修。

**本轮踩到的两个坑（记录以免重犯）**：
- `get_model_state_dict(..., StateDictOptions(full_state_dict=True))` 是**集合通信**。
  我在探针里只让 rank 0 调用，rank 0 就永远等一个不会加入的集合通信，表现是
  **整体挂死**而不是报错。同样的道理写在 `parallel.fsdp.clip_grad_norm_` 的注释里。
- `PipelineStage` 有 `parameters()` 但没有 `named_parameters()`；PP 的 worker 用例
  一开始直接调后者，`AttributeError`。

**验收**：215 passed（+2 条参数化用例，其中 PP 那条带 6.4e-01 的反证）；
`ruff` 90（未新增）；3 契约 kept；新增覆盖：TP/PP 往返、重分片到单进程。

**Stage D（PP → `torch.distributed.pipelining`）仍未开始**，阻塞条件不变
（本机 2 rank 下原生 PP 触发 gloo 传输层硬崩溃，根因未定位）。本阶段的 PP 修复
与它无关：现有自研 PP 是工作的，只是它的 key 命名需要命名空间。

## Stage D 阻塞项的根因（2026-09-16，已定位，未实施迁移）

方案里 Stage D（PP 换成 `torch.distributed.pipelining`）被阻塞在一个未诊断的
硬崩溃上。**根因已定位**，解阻条件满足，但迁移本身**没有做**——理由见本节末。

### 症状与最小复现

`PipelineStage` + `ScheduleGPipe` 构建正常，`sched.step()` 时两个 rank 同时
`libc++abi: terminating`，无 Python 异常。最小复现：2 rank、Gloo/CPU、一层
Linear、`n_microbatches=1/2/4` **全部**复现（所以与 microbatch 数无关）。

### 根因：torch 自己的握手张量 dtype 不匹配

定位方法：把 `_get_init_p2p_neighbors_ops`（`pipelining/stage.py:938`）里的两个张量
原样拿出来，手工做一次同样的 P2P 交换。它构造的是：

```python
recv_tensor = torch.zeros(1, device=self.device)              # float32，4 字节
send_tensor = torch.tensor(self.stage_index, device=self.device)  # int64，  8 字节
```

一发一收按**元素个数**看都是 1，按**字节**看是 8 对 4。Gloo 的 UV 传输层按字节
校验（`op.nread == op.preamble.nbytes`），于是直接 abort 进程。

对照实验（同样两个 rank、同样一次 `batch_isend_irecv`）：

| 交换内容 | 结果 |
|---|---|
| int64 发 / float32 收（torch 现在构造的） | **同样的硬崩溃** |
| 两端 dtype 一致 | **正常完成** |

### 这个握手是「哑」的，所以修它是安全的

该方法由 [pytorch#160210](https://github.com/pytorch/pytorch/commit/e63c2b21c186a7d2ab8a8953b8aa1535f2e96e58)
引入，动机是 **NCCL 多机 hang**：提前把 batched P2P 需要的通信器建好。它传的张量
内容**无所谓**，起作用的是「第一次 batched P2P 走全局 group」这件事。NCCL 那边
只看元素个数（两边都是 1），所以这个 dtype 不匹配一直没被发现；Gloo 的 UV 传输
按字节校验，就炸了。

把两个张量改成同一种 dtype（如都 `torch.zeros(1)`）后，**PP=2 端到端跑通，且梯度与
单进程参考逐位相同（`max|diff| = 0.000e+00`）**，loss 也正常。

### 为什么仍然不做这次迁移

解阻条件说的是「解阻后再评估」，评估结果是**不做**：

1. **修复必须靠 monkeypatch torch 私有方法。** 一旦 torch 改了这个方法名，补丁会
   **静默变成空操作**，崩溃以「进程直接 abort」的形式回来。为一个未修复的上游 bug
   长期背这个包袱，需要有明确收益来换。
2. **在本机可验证的收益是零。** 现有自研 PP 与单进程逐位相同（`0.000e+00`），
   打补丁的原生 PP 也是 `0.000e+00`。两者在能测到的范围内没有差别。
3. **真正值得换的功能（zero-bubble / interleaved）在本机无法验证**——需要 2 个以上
   stage 和 CUDA/NCCL。
4. **替换面很大**：`pp_schedule.py`(425) + `pp_p2p.py`(257) + `PipelineStage` 的生产
   `pipeline_step` + 17 条协议测试 + 4 条多卡用例 + `parallel_matrix` + 示例。

**结论**：记录根因与补丁配方，等有 CUDA/NCCL 机器、或上游修好之后再做。届时这是一件
已知工作量的事，而不是一次考古。

## DP+TP+PP+SP 全轴训练与分片存取（2026-09-16）

目标是把四个轴同时打开，训练与分片 checkpoint 都正确。做下来有两处修复，
**其中一处的影响面远超本目标**。

### 一、`pp` 与 `tp` 无法组合：`split_sequential` 重编号

`split_sequential` 用 `nn.Sequential(*layers[...])` 建 stage，按位置把子模块重命名成
`0, 1, …`。实测 stage 的 FQN 是 `['0', '1']`，于是按后缀匹配的 TP plan 一个都找不到。

改成 `PipelineSequence`（保留原名）后：

- TP plan 能在 stage 上匹配到 `q_proj`/`o_proj` → `tp=2,pp=2` 的通路打开；
- 各 stage 的 checkpoint key 不再撞名 → `checkpointing._stage_prefix` 这个绕行**删除**，
  且删掉后 PP 往返仍是 `0.000e+00`（证明名字唯一本身就够，不是靠前缀兜底）。

**反向对照**：把 `nn.Sequential` 换回去 → 「stage children are named by position again:
`['0.o_proj.bias', ...]`」，7 个组合变红（含四轴全开）。

### 二、`Runtime` 按 rank 偏移 seed：各 rank 建出**不同的模型**

这是本次最重要的发现，且**与 PP/TP 无关**——它影响所有多卡用法。

`runtime.py` 曾经是 `seed_everything(seed + self.state.rank)`。它 seed 的是**全局 RNG**，
而调用方正是从全局 RNG 取模型初始化。本仓所有示例、以及 `Trainer.__init__` 自己的
docstring 都推荐「先建 `Runtime` 再建模型」——那正是会踩中的用法。

实测（world=2）：

| 证据 | 值 |
|---|---|
| `torch.initial_seed()` rank0 / rank1 | `1234` / `1235` |
| 同一个模型，**训练前** | `max\|dW\| = 6.9e-01` |
| `dp=2` 训练后 vs 单进程参考 | `6.34e-01` |
| `pp=2` 训练后 vs 单进程参考 | `6.91e-01` |
| **`tp=2` 训练后 vs 单进程参考** | **`2.98e-08`（掩盖住了）** |

两件事把它藏住了：**TP** 的 `distribute_tensor` 从 `src_data_rank` 广播参数，直接覆盖差异；
**FSDP** 的 all-gather 把两个 rank 各一半拼成一个「看起来正常」的模型。**PP** 两样都没有，
所以是它暴露的。`tp=2` 在反向对照里**仍然通过**，正是这个掩盖的直接证据。

数据分片本来就由调用方负责（`seed_everything` 的 docstring 一直这么写：「callers remain
responsible for data samplers」），所以这个偏移没有换来任何东西。改为 `seed_everything(seed)`：
rank 0 行为不变，单进程完全不受影响。

**反向对照**：改回 `seed + rank` → 7 个变红（`dp`/`pp`/四轴全开），`tp=2` 依旧绿。

### 三、`pp` + `tp` 的结构约束（不是缺陷，是必须遵守的写法）

每个 stage 内部必须有完整的 col→row 配对。column 输出分片激活，跨 PP 边界传的是完整
张量，对端的 row 会把它当成分片。实测把 column 与它的 row 分到不同 stage 时 `fit`
**死锁**（Gloo recv 超时），不报形状错。每个 top-level child 就是一个 norm+col+row 单元
时四轴全开成立。

### 验收

`dp=2,tp=2,pp=2`（world=8）与再加 `sp=megatron`：
- **训练**后与单进程参考 `max|diff| = 2.98e-08`
- **分片 checkpoint 往返** `max|dW| = 0.0e+00`

236 passed；ruff 90（未新增）；3 契约 kept。

### 一处自身的失误，记录以免重犯

用「整段替换」（`s[:start] + new`）改 `test_multirank_gloo.py` 时丢掉了一个已有测试
（`test_sharded_checkpoint_reshards_to_a_single_process`），**当时没注意到**——它既没进
git，也没被测试数下降暴露（新加的用例把总数补上了）。本轮的教训：整段替换后必须核对
测试集合，不能只看 passed 数。

## 预训练权重加载：读取行为实测（2026-09-16）

用户问的是「加载预训练模型时，分片是否支持每 rank 从 CPU 直读自己的分片，而不是
rank0 完整加载再广播」。**答案是：三条路径都不是 rank0 广播**，实测如下。

| 路径 | 每 rank 读什么 | rank0 中转 |
|---|---|---|
| `Trainer.load_sharded`（DCP） | 只读自己需要的区间 | 无 |
| `convert` + `load_for_rank` | 只读自己的分片文件 | 无（docstring 明写 no rank-0 broadcast） |
| `Trainer.load_checkpoint`（非分片） | 自己那份**完整** `rank_state.pt` | 无，但 **IO 放大 N 倍** |

**证据**（tp=2、`Linear(64,64)`）：`load_sharded` 的读取项 offset——

| 参数 | rank 0 | rank 1 |
|---|---|---|
| `q_proj.weight`（列并行） | `(0,0)` | `(32,0)` |
| `q_proj.bias` | `(0,)` | `(32,)` |
| `o_proj.weight`（行并行） | `(0,0)` | `(0,32)` |
| `o_proj.bias`（复制） | `(0,)` | `(0,)` |

DCP 的读取是**分摊**的（`DefaultLoadPlanner.create_global_plan` 汇总各 rank 需求再分配），
所以别的拓扑下分配未必一一对应，但**没有 rank 读全部**。

### 本轮补上的：`stage_assignment` 自动派生

`convert` 在 `pp_size>1` 时要调用方给 `stage_assignment`，否则拒绝（理由正确：dense
state dict 看不出层属于哪个 stage）。但框架自己知道——它训练时就做这个切分。
新增 `parallel.pp_shapes.stage_assignment(model, pp_size)`，跑**同一个**
`split_sequential` 得出映射，checkpoint 与训练不会分歧。`convert` 的报错文案也指向它。

它能成立的前提是 `PipelineSequence` 保留原名；用旧的按位置重编号，每个 stage 都报
`0.weight`，派生出来的映射会是一堆同名的 `0.weight`——**而且不会报错**。

验收：单进程两条（映射内容 + 端到端 convert），另有一条多阶段的加载实测
（`pp_rank=0/1` 各自只读自己的分片，`bytes_read` 各 288，数值 `0.0e+00`）。

### 下一步（用户提出、已实测可行）

用户提出：**先构造 FSDP，每个 rank 再加载自己那一片**，这样 DP 轴也不必复制。
实测成立——在已 `fully_shard` 的模型上，每 rank 按 `(pp,tp,dp)` 取自己那一段、
经 `param.to_local().copy_(local)` 写进本地 storage（需 `no_grad`），
`full_tensor()` 能**精确重建**完整权重（`max|diff| = 0.000e+00`）。

这把 DP 从「复制」变成「切分」，是路线图 §「模型初始化」一节已经写明的方向
（「再传输到本地参数、DTensor 或 FSDP storage」）。尚未接线。

## 预训练权重按拓扑分片加载（2026-09-16）

用户的目标：训练开始时加载预训练模型，**每个 rank 从 CPU 直读自己那一片**，
而不是 rank0 完整加载再广播。已交付。

```python
plan = TransformerTPPlan()
CheckpointConverter(partition_dims=plan.partition_dims(model)).convert(
    "pytorch_model.pt", "sharded/", dp_size=2, tp_size=2, pp_size=2,
    dp_sharded=True, stage_assignment=stage_assignment(model, 2))
trainer.load_pretrained("sharded/manifest.json")
```

实测每 rank 读取量随拓扑按 `1/(dp·tp·pp)` 下降（完整模型 2304 字节）：

| 组合 | 每 rank | 比例 |
|---|---|---|
| `dp=2` / `tp=2` / `pp=2` | 1152 / 1216 / 1152 | ~1/2 |
| `dp=2,tp=2` / `tp=2,pp=2` / `dp=2,pp=2` | 608 / 608 / 576 | ~1/4 |
| `dp=2,tp=2,pp=2` | **304** | **1/8** |

三个前提，每个都有实测支撑：

1. **DP 参与分片，但只在 FSDP 时成立**，且 manifest 与加载方必须一致——不一致就报错。
   DP 是复制时每 rank 需要完整参数、文件里却是切片，反过来同理，两种都会**静默**给出
   残缺模型。manifest 新增 `dp_sharded` 字段承载这个声明。
2. **`partition_dims` 决定 IO 省不省**。不给它，convert 把所有张量记成 replicated
   （实测：每 rank `bytes_read` = 完整模型的 2304），加载正确但什么都没省。
   `TransformerTPPlan().partition_dims(model)` 镜像 torch style 的真实行为派生它。
3. **布局不一致时报错，不猜**。`_assign` 按形状区分「这是我本地那片」（直接写）与
   「这是完整张量」（DTensor redistribute），都不是就报错。

**反向对照**：把 `partition_dims` 去掉 → `rank 0 read 2304 bytes for a 2304-byte model
-- it read everything` 变红；`dp=2,tp=2` 则是形状不符的显式拒绝（说明没有静默切错）。
4 红 3 绿，只有需要切分的组合变红。

### 顺带修掉一个静默丢字段的缺陷

`Manifest.from_dict` 逐字段取值，`dp_sharded` 加进了 dataclass 和 `to_dict`
（用 `asdict`）却漏在 `from_dict` 里：manifest **写进了 JSON**，读回来是默认的
`False`，加载方于是报「converted with dp_sharded=False」——字段就在文件里。
新增 `test_manifest_round_trip_keeps_every_field` 用 `dataclasses.fields()` 驱动往返，
以后再加字段忘了序列化会直接变红。

### 一处自身的失误

`reader.py` 里连做两次 `write_text`，第二次用了**旧内容**，把第一次的结果覆盖掉了
（表现为 `_assign() got an unexpected keyword argument`）。整段替换的编辑方式在这个
会话里已出过两次问题（另一次是丢掉一个测试）。教训同上：改完要跑，不能只看编辑成功。

**验收**：246 passed（+7 条按拓扑参数化的加载用例）；ruff 未新增；3 契约 kept；7 示例通过。

## 死配置字段的清零，以及一条拦住它的测试（2026-09-16）

`precision.reduce_dtype` 被实测确认**对训练没有任何影响**，四条路径上只改它、结果逐位相同：

| 路径 | float32 vs bfloat16 | 参数类型 |
|---|---|---|
| 单进程 | `0.000e+00` | Tensor |
| FSDP（world=1） | `0.000e+00` | Tensor |
| dp=2 —— FSDP 梯度归约 | `0.000e+00` | DTensor |
| tp=2 —— row 投影 all-reduce | `0.000e+00` | DTensor |

最后一条是它 docstring 明确声称接的地方。**灵敏度对照**：人为把 bf16 接进 FSDP 的
`MixedPrecisionPolicy(reduce_dtype=...)` 后结果改变 `1.69e-02`——所以 `0.000` 是「真的
没接」，不是「测不出来」。四条路径的参数都是 `DTensor`，即分片确实生效。

**它不是从来没接过，而是被迁移掐断的**：`git show 0b28273:src/aitrainer/parallel/tp.py`
里 `RowParallelLinear.__init__(reduce_dtype=...)` → `reduce_from_tp(..., reduce_dtype=self.reduce_dtype)`
是真的接线；迁移提交 `773107d` 把这些行整体删除，换成不接受 dtype 的 `RowwiseParallel`。
**接线走了，字段和关于它的一切都留下了**——字段、`validate()` 的校验项、两个设置它的
preset、以及那句 docstring。校验尤其毒：设一个非法值会**报错**，于是它看起来比真字段还
真。（§5.2 那条「已修」记录的正是迁移前的那次修复，已更新。）

它的净效果是：用 `ConfigPreset.performance()` 或 `memory_saving()` 的人以为开了 bf16
归约，在所有输出里也看到 `'reduce_dtype': 'bfloat16'`，而计算全程 fp32。

**处置**：删除字段、那句 docstring、`validate()` 的校验项、两个 preset 里的设置，以及
`examples/config.json` 里的一行。

### 顺带删掉同类的最后一个

用 AST 精确扫描「配置字段在 `schema.py` 之外有没有读取点」（属性访问 `.field` 或
`getattr(obj, "field")`；**字段自己的类型校验不算**——那恰恰是死字段唯一剩下的痕迹），
删掉 `reduce_dtype` 后 39 个叶子字段里只剩一个：`overlap.enable_parameter_prefetch`。

它比 `reduce_dtype` 更彻底地死：其余五个高级 overlap 开关至少还进 `capability.py` 的拒绝
守卫（`架构.md` §4 说它们「仅拒绝用」），而这一个**连拒绝作用都没有**，唯一读它的是它自己
的类型检查。对照组 `enable_transfer_overlap` 真的被 `offload/manager.py:29` 读——即那个位置
本该有读取点。一并删除。

### 拦住的测试

`test_every_config_field_is_read_somewhere`：枚举 `FrameworkConfig` 的全部叶子字段，AST 扫描

这条测试值当，因为这个缺陷类型在本仓已出现**至少七次**：`param_dtype`、`reduce_dtype`、
`FSDPConfig.sharding` / `limit_all_gathers` / `forward_prefetch` / `execution_trace_complete`、

## 分片 checkpoint 补齐 scheduler / scaler / sampler（2026-09-16）

上一轮修了分片路径的 RNG，但**同一处缺口还有三个字段**：`save_sharded` 只写
model/optimizer/bookkeeping，而非分片的 `save_checkpoint` 另外存 scheduler、scaler 和
sampler 位置。这一轮补齐，两个格式现在携带同样的内容。

**scheduler 缺口的实测**（`CosineAnnealingLR(T_max=10)`，跑 4 步后各续训 2 步）：

| 来源 | `last_epoch` | 续训 2 步后的 lr |
|---|---|---|
| 参考 run | 4 | 应为 0.034549 |
| per-rank 格式 | 6 | **0.034549** ✓ |
| 分片格式 | 2 | **0.059201** ✗ |

**为什么此前没被发现**：`lr` 随 optimizer 的 `param_groups` 回来了，而 `StepLR` 是在
**当前 lr** 上乘系数、不是从 `last_epoch` 算——所以 StepLR 的用户**碰巧**完全正确。
第一版探针我用 StepLR 测，两种格式给出同样的结果，差点得出「没问题」的结论；换成按
`last_epoch` 算绝对值的调度器才暴露。**测一个性质时要选能让它失败的对象。**

**sampler 只能暂存**：provider 是 `fit` 的 `data` 参数，续训的写法是先 `load_sharded()` 再
`fit(data)`，所以加载时没有 provider 可写。其状态以 **bytes**（非张量）存进 DCP——实测
DCP 对非张量值是**整体替换**（列表长度、甚至类型不一致都不校验，占位写什么都行），张量
才必须与存档形状完全一致。`load_sharded` 把它挂在 trainer 上，由**恰好一次** `fit` 取用。

### 顺带加的守卫，以及第一版写错了

DCP 按 recipe 逐键填充：checkpoint 里有、recipe 里没有的条目不报错、只是不读。所以
「存了、没认领」会丢掉一个命名空间而看起来一切正常。加载前比对键集即可。

**第一版守卫按「键」比较，被实测否掉**：分片 checkpoint 在各 rank 上是**分区**的，而
`read_metadata()` 报**全局**键集——流水线 stage 持有 `model.unit0.*` 而元数据里还有 stage 1
的 `model.unit2.*`，RNG 按坐标命名空间。于是每个正常 checkpoint 都被拒：实测 `dp2-pp2`
下 48 条误报、`dp2-tp2-pp2` 同样红，7 条既有测试变红。改成按**命名空间**比较（`model.`
`rng.` `scheduler` …）后恰好抓住真正发生过的那类失败。**误报和漏报一样是缺陷，只是更早暴露。**

`_flatten_keys` 照 `torch/.../_traverse.py` 重写（不 import 私有模块），
`test_flatten_keys_matches_torch` 用真实存档把两者钉住。规则里唯一不显然的是**列表何时算
一个值**：DCP 只在列表装着可下钻内容时才下钻，`base_lrs=[0.1, 0.1]` 是**一个**键。

### 顺带修掉的文档漂移

同一节里 `架构.md` 第 194 行仍把 `checkpointing._stage_prefix` 当成 PP 的现行机制，而
第 275 行自己写着「已删除」——同文自相矛盾。已改为描述真正的原因（`PipelineSequence`
保留原名，各 stage 的 key 天然不撞）。

## 随机状态审计，以及它查出的两个静默缺陷（2026-09-16）

用户提出的问题：多机多卡、尤其组合轴下，随机状态最容易静默出错——FSDP full-shard 时各机
初始化的权重可能不一致，相同 sp_rank 的随机流可能不同步，于是数据加载不一致、随机算子
不一致，训练不收敛而**没有任何报错**。要求分析各分片策略的潜在问题，并给出**可运行的验证脚本**。

交付 `scripts/verify_random_state.py`：显式 rendezvous 起真进程，逐项检查并打印**每个 rank**
的一行结论（失败时点名轴与 rank，而不是「训练发散了」）。2 rank 实测：

| 检查 | 结果 |
|---|---|
| `init` —— 各 rank 建出的模型 | ✓ `seed=1234`，逐位相同 |
| `rng-sync` —— forward 前后各 rank 的 RNG | ✓ 同步 |
| `sp-dropout` —— SP 区域 vs 单进程 | ✓ `5.96e-08` |
| `data-shard` —— dp 各 rank 能否分片 | ✗ → 已修 |
| `checkpoint-rng` —— 续训后的随机流 | 非分片 ✓ / 分片 ✗ → 已修 |

审计本身查出的**两个静默缺陷**（详述见 `架构.md` §6）：

1. **数据没有按 dp rank 分片。** `loop.py` / `evaluation.py` 恒传 `dp_group=None`，provider
   拿不到 rank，只能每个 rank 遍历整个数据集——数据并行退化成 N 份相同梯度的平均，花 N 倍
   算力换一个 rank 的批次。修法：`Trainer.dp_process_group()` 复用 `parallelize` 已建好的
   mesh（**不新建**——`new_group` 是集合操作，重复一份轻则浪费、重则顺序不同而挂死）。
2. **分片 checkpoint 不保存 RNG。** 两个格式现在都存 `torch`+`python` 两个流并都恢复。

两个具体做法不是显然的，记下来：

- **RNG 状态按坐标命名空间化**（key = `rng.{pp}.{tp}.{dp}`）：随机状态是 per-rank 的，各 rank
  本就不同，共用 key 会让 DCP 把某一个 rank 的值当成**唯一**的值发给所有人。
- **Python 的 RNG 状态不能靠 pickle。** DCP 用交给它的 state dict 的**形状**决定读多少字节，
  所以占位与保存的形状必须一致，而 `random.getstate()` 的 pickle **长度会变**（缓存 gauss 从
  `None` 变成 float）——实测保存 3752 字节、加载 3829 字节，DCP 报 `Size mismatch between saved
  torch.Size([3752]) and current torch.Size([3829])`。改为拆开存 version + 625 个 word + gauss
  （`None` 记 NaN），形状全固定。

**两条负面教训，都已写进测试注释与 `架构.md`：**

- **检查 helper 而漏掉调用点。** 只断言 `dp_process_group()` 非 None，即使 `fit` 仍传 `None`
  也全绿。现在多卡用例用一个**记录型 provider** 报告 `fit`/`evaluate` 实际传下去的是什么，
  并断言各 rank 的 `dist.get_rank(group)` 互不相同（provider 就是靠这个分片的）。
- **测试自己写错了。** `test_sharded_checkpoint_restores_the_random_stream` 第一版在**同一次
  run** 里先抽 `expected` 再保存——保存下来的流已经越过那些抽取，于是与完全正确的实现比较
  也不等，把好实现报成了坏的。正确形状是两次相同 run：第一次当参考，第二次 fit 到同一点、
  保存、把流挪走、再加载。

**反向对照（每条都做过）**：`save_sharded` 去掉 RNG 键 → 红（DCP 显式报缺 key）；两侧都去掉
→ 断言红，不是静默；`fit` 改回 `dp_group=None` → 红。`scripts/verify_random_state.py` 现已同时
测量 torch 与 python 两个流。

**验收**：249 passed（+2）；ruff 90（基线未变）；3 契约 kept；审计 `failures: 0`。

**第二轮审查追加修复**
- **HIGH · 又一处我的回归**：`ConfigPreset.memory_saving()` 曾在**第一步就崩**（`PrecisionError`）。我在 Stage D 为了区分两个 preset 给它设了 `grad_dtype="bfloat16"`，但 `param_dtype` 是死字段（参数仍是 fp32），而 `cast_gradients` 要求梯度与参数 dtype 一致 → 该组合永不可满足。现改为在**活的** `optimizer_dtype` 上区分（memory_saving 用 bf16 优化器状态，Adam 两个动量减半），`grad_dtype` 保持 fp32

### 2.3 `OverlapController.submit()` 在 disabled 时不记账（根因 C）

### 2.4 多卡（≥3 rank）作业在组创建阶段死锁

**证据链**（`src/aitrainer/parallel/groups.py:42-45`）：

```python
for axis in ("pp", "dp", "tp"):
    axis_ranks = mapping.group_ranks(axis, coord)   # coord 是「本 rank」的坐标
    groups[axis] = dist.new_group(list(axis_ranks))
```

每个 rank **只创建自己的组**，因此在第 k 次调用时，不同 rank 传入的是**不同的 rank 列表**。

**机制（已从 torch 源码确认）**：默认 `use_local_synchronization=False` 时，`torch/distributed/distributed_c10d.py` 的 `_process_group_name`（`:5015-5024`）返回 `pg_name = str(_world.group_count)` —— 一个**每进程调用计数器**。于是每个 rank 的第 k 次 `new_group` 都落在 store 命名空间 `k` 中，**与它传入哪个 rank 列表无关**。而 `_store_based_barrier`（`:928-993`）为每个 `group_name` 只用一个计数键，每个参与者 `store.add(store_key, 1)`，只有观察到 `worker_count == rendezvous_count`（该组的**大小**）的 rank 才会设置 `last_worker_key`。

→ 当同一索引处的不同 rank 集合**大小不同**时（world=4、pp=1/dp=2/tp=2：计数器 0 → 四个 1-rank 组；1 和 2 → 两个 2-rank 组），共享计数器会**跳过**期望值 → 没有任何 rank 观察到 `worker_count == rendezvous_count` → **没有任何 rank 设置 `last_worker_key`** → 每个参与者阻塞到 gloo 默认超时（1800000 ms = **30 分钟**）后报错。同一索引处多个进程的读回存在竞态，故该问题**间歇性**。

`world_size <= 2` 在实践中安全（首个读回者总能恰好观察到期望计数）；问题从 **3-4 个 rank** 开始。

**复现证据（干净 A/B，同一环境，✅审计者已核验产物）**：

| 分支 | 做法 | 结果 |
|---|---|---|
| 规范顺序 | 所有 rank 以固定顺序创建全部 8 个组 | `canon4.txt` → **4/4** rank 打印 `ALL DONE` |
| 按 rank 顺序 | 完全复刻 `groups.py:42-45`（每 rank 只建自己的 pp/dp/tp 组） | `perrank4.txt` → **0/4** 到达 `ALL DONE`；日志在建组中途停住，2/2 次运行停滞 |

**真实代码路径**（world=4，pp=1/dp=2/tp=2，走 `DeviceMeshManager` → `ProcessGroups.create`）：

```
R4 rank 0: tp_pg [0,1] ok | dp_pg [0,2] ok | pp_pg [0] ok
R4 rank 1: tp_pg [0,1] ok | dp_pg [1,3] ok | pp_pg [1] ok
R4 rank 2: (未打印 — 仍在 new_group 内)
R4 rank 3: (未打印 — 仍在 new_group 内)
... dist.barrier() -> RuntimeError: Timed out waiting 1800000ms for send operation to complete
       (gloo/transport/uv/unbound_buffer.cc:101)
```

该超时错误在产物 `out5.txt` 中可直接读到。

**影响**：≥3 rank 的作业在组创建阶段**死锁**，每次尝试浪费 30 分钟；而 rank 0/1 创建的成员关系**本身是正确的**，极具误导性。这与项目自己的第 3 条设计原则（"拒绝，而不是静默降级"）相悖。

**修复**（均可在源码验证）：传 `use_local_synchronization=True`（此时用 `_hash_ranks_to_str(ranks)` 按 rank 列表命名，`:5018-5019`，冲突消失），或按规范顺序创建全部组（已验证 4/4 通过）。

> **附注（置信度降级）**：曾有假设认为在 NCCL 上会表现为"配对错误的通信器"而非卡住 —— 该变体**未经验证**，应记为 `SUSPECT`。同一 store 竞争的另一后果是某 rank 可能被**另一个**组的签到提前解除阻塞、在其自身组员全部加入前就从 `new_group` 返回，从而得到成员不完整的组；但实测观察到的是**卡住**，不是这个。

## 3. P0 缺陷：静默错误（比崩溃更危险）

### 3.1 PP 路径从不除以 `grad_accumulation_steps` → 等效学习率 ×N

**证据链**：两条路径不对称。

| 路径 | 位置 | 是否除以累积步数 |
|---|---|---|
| 非 PP | `trainer.py:220` `scaled_loss = loss / self.config.grad_accumulation_steps` | ✅ |
| PP | `trainer.py:158-198` `_pipeline_train_step` | ❌ 整条路径无等价除法 |

而 `trainer.py:171` 照样按累积边界决定 step：

```python
should_step = self.global_step % self.config.grad_accumulation_steps == 0
```

`docs/设计文档.md:268` 明确写着契约是 `loss = output.loss / grad_accumulation_steps` —— **实现违背自身文档**。

**影响**：`pp_size>1` + `grad_accumulation_steps=N>1` 时，N 个 step 的梯度被**求和**后更新，每次参数更新恰好比 `pp_size=1` 的同配置大 **N 倍**。默认 `grad_accumulation_steps=1` 掩盖了它。此结论由审计者 📖**代码确证**，并由 PP 分审计从独立的进程内模拟路径复现。

### 3.2 参数 offload 首次 `train_step` 即 `KeyError`，功能 100% 不可用

## 7. 可用性缺口：为了真实可用还缺什么

### 7.1 阻塞级（不解决则无法用于任何真实任务）

1. **TP/SP 全崩（§2.1）** —— 修 `forward` 参数数（3 处）+ `reduce_dtype` 作用域，然后**把测试跑起来**。当前最高的单项。
2. **元组 batch 契约破损（§2.2）** —— `train_step((x, y))` 是文档主推用法，却要求模型的 `forward` 必须恰好接受 2 个位置参数。修复方向：`self.model(*batch)` 应只传输入，或在契约中明确要求模型签名。
3. **数据层不存在** —— 全仓库零个 `Dataset`/`DataLoader`/`tokenizer`/`from_pretrained`（grep 验证），所有示例都是 `torch.randn`/`randint`。`data.py` 是契约外壳：`DataProviderAdapter`（`:89-114`）**不构造** `DataLoader`，只调用用户传入的 `loader_factory(dp_group=..., seed=..., epoch=...)`。**没有任何从磁盘数据到训练的路径。**
4. **配置示例 + schema** —— `validate --config config.json` 是用户第一个会试的命令，而仓库里没有任何 JSON，也没有 schema 表。
5. **`evaluate()` 的分布式语义（§3.7）** —— 无跨 rank 归约、复用训练集 loader、PP 下返回 NaN。**静默错误的指标比没有指标更糟。**
6. **权重初始化不可复现（§3.8）** —— `seed` 在模型构造之后才生效。
7. **示例可运行性** —— ✅实测 7 个示例中 3 个崩溃（`tp_train`、`pp_train`、`offload_train`），`fsdp_train` 需 torchrun，只有 `tiny_transformer` 真正训练。
8. **多卡（≥3 rank）作业死锁（§2.4）** —— 组创建阶段的 store 命名空间冲突让 ≥3 rank 的作业在启动时挂死 30 分钟后报错。`world_size<=2` 安全，这正是"只在 2 卡上试过"会漏掉它的原因。修 `groups.py:42-45` 是**多卡可用的前置条件**。

### 7.2 其次

8. **许可证与 provenance** —— 无 `LICENSE`；`references/uylesses` 是阿里 Wan2.1 的代码拷贝（5 文件 / 320 行，每文件带 `Copyright 2024-2025 The Alibaba Wan Team`），**但没有 LICENSE 文件** —— 而 `docs/设计文档.md` §14 自己要求"实际移植必须保留 NOTICE、许可证审查记录和版本锁定信息"。且该目录作为包无法导入（`from ..modules.attention import ...` 的上级包不存在），是功能切片而非完整仓库。（对照：`references/DeepSpeed` 495M 完整 clone v0.19.5-46，`references/Megatron-LM` 196M 完整 clone core_v0.15.0rc7，二者纯作机制参考，并由 `scripts/check_no_reference_imports.py` 的 AST 检查**机械保证**不被 import。）
9. **`git init` 并让 CI 真的跑** —— 当前 CI 若执行会红 10 个测试；且因为无 `.git`，它从未执行过。需补 GPU/torchrun job。
10. **英文文档** —— 两份设计文档均为中文；无 API reference、无 `CONTRIBUTING`、无 `CHANGELOG`、无版本号（README 用 "Batch" 计数）。
11. **Profiler 接线或降级标签**；修正 `kernel_eager_fallback`/`planning_report`/`overlap_metrics` 三个不可达的 `STABLE` 标签。
12. **checkpoint 硬化（§4.7）** —— 真正校验 checksum、比对 `logical_sharding` 而非只比总数、`selected` 为空时报错、converter 切分 PP。
13. **真实预训练权重加载** —— `Llama/GPT/BERT` 适配器经 `_build()` 用 `nn.TransformerEncoderLayer` **随机初始化**（模块 docstring 诚实地说了，README 未标注）；`CheckpointConverter`（`converter.py`，约 600 行）与 `ModelLoader` 是完整实现但**除测试外无任何调用方**。
14. **推理/导出** —— 完全没有（无 `predict`、无 ONNX/TorchScript、无生成循环、无 tokenizer）。纯训练框架。

### 7.3 最小可行路径（按依赖顺序）

1. 修 TP/SP `forward` 参数数（§2.1）+ `reduce_dtype` 作用域

## 9. 总评

这个仓库的**工程纪律是真诚的**：能力分级、fail-fast 校验、原子 checkpoint 发布、禁止 import 参考仓库的 AST 守卫、"未验证不得标记完成"的规范、README 主动标注 Batch 1 待验证。这些比许多成熟项目做得好。

但代码的真实状态与文档的差距比预期**大一个数量级**：不是"边缘功能未接线"，而是 **TP 与 SP 两个核心能力在任何 world size 下都抛异常**，且 **仓库自己的测试套件在装上 torch 后立刻红 10 个**（其中 5 个由框架自身的 batch 契约缺陷导致）。这解释了一切 —— 这套 6.4k 行代码是在**没有 torch 的机器上**写出来的，所有分布式能力从未被执行过一次。`待验证` 标签是诚实的，但它覆盖的范围比作者以为的广得多。

一条元教训：`pytest.importorskip("torch")` + 无 torch 的开发环境 = **一套静默全绿的测试**。CI 存在、断言存在、纪律存在，但唯一的信号通道是断的。
